# §1 — უცვლელი წესები / Non-negotiable rules

ეს 10 წესი ჭრის ყველა სხვა ინსტრუქციას:

1. **მტკიცებულება ან არაფერი.** ყოველ მიგნებას უნდა ახლდეს `ფაილი:ხაზი` და
   ციტატა რეალურად წაკითხული კოდიდან. ვარაუდი, "ჩვეულებრივ ასეთ პროექტებში",
   "სავარაუდოდ" — აკრძალულია.
2. **დოკუმენტაცია არ არის მტკიცებულება.** `CLAUDE.md`, `README.md`,
   `docs/PRODUCTION_HANDOVER.md`, `docs/OPUS5_AUDIT_*.md` და კომენტარები კოდში
   შეიძლება იყოს მოძველებული ან არასწორი. ისინი მხოლოდ **ჰიპოთეზების წყაროა**.
   ყოველი მტკიცება გადაამოწმე თავად კოდში.
3. **მწვანე ტესტი არ ნიშნავს სწორ ქცევას.** თუ ტესტი გადის, იკითხე: *რას
   ამოწმებს სინამდვილეში?* მრავალი ხარვეზი ამ რეპოში სწორედ მწვანე ტესტების
   ქვეშ იმალებოდა (იხ. `.github/workflows/ci.yml`-ის კომენტარი PR-01-ზე).
4. **ორი სტეკი, ერთი პროდუქტი.** რეპოში ცხოვრობს **ორი** სამუშაო
   იმპლემენტაცია: legacy Python/FastAPI + SQLite/Postgres და ახალი
   Java/Spring Boot + Oracle + Angular. ჯერ **დაადგინე რომელი მიდის
   პროდაქშენში**, შემდეგ დაასაბუთე ეს დასკვნა. მეორის ხარვეზი სხვა
   სიმძიმისაა — მაგრამ სულაც არ არის უწყინარი (იხ. §3.A).
5. **CONFIRMED vs SUSPECTED.** ყოველი მიგნება მონიშნე ერთით:
   - `CONFIRMED` — მაქვს კონკრეტული კოდი + კონკრეტული სცენარი, სადაც ის
     მცდარად იქცევა; ან რეალურად გავუშვი და ვნახე.
   - `SUSPECTED` — კოდი საეჭვოა, მაგრამ ვერ დავამტკიცე. აუცილებლად დაწერე,
     **რა შემოწმება დაასრულებდა საკითხს**.
   არასდროს არ გაასაღო `SUSPECTED` როგორც `CONFIRMED`.
6. **ყოველ მიგნებას სჭირდება ჩავარდნის სცენარი.** კონკრეტული: "მენეჯერი X
   დეპარტამენტიდან აჭერს ღილაკს Y → იღებს Z-ს, უნდა მიეღოს W". თუ ვერ წერ
   ასეთ სცენარს — ეს არ არის მიგნება, ეს არის გემოვნება; ამოაგდე.
7. **გემოვნებაზე არ ვწერთ.** დასახელების სტილი, ფორმატირება, "უკეთესი
   არქიტექტურა", "აქ Repository Pattern ჯობდა" — ამ ანგარიშში არ შედის, თუ
   მას არ მოსდევს რეალური, დღეს არსებული დეფექტი.
8. **არაფერს ცვლი.** არც ერთი `Edit`/`Write` სამუშაო კოდზე. არც `git commit`,
   არც `git push`. ერთადერთი ჩანაწერი — საბოლოო ანგარიშის ფაილი.
9. **ორენოვნება.** ანგარიშის სათაურები და არატექნიკური შეჯამება — ქართულად;

   დეველოპერიც და არატექნიკური პროექტის მფლობელიც.
10. **ჭეშმარიტება > კომფორტი.** თუ პროდუქტი მზად არ არის — თქვი პირდაპირ.

  **საერთოდ არ არის მითითებული**? fail-safe თუ fail-open?

- **პაროლები:** hashing (bcrypt round-ები), მინიმალური სირთულე,
  ბრუტფორსის დაცვა, პაროლის აღდგენის ნაკადი (ან მისი არარსებობა).
- **Rate limiting:** სად არის, რაზეა დაკავშირებული (IP? user? global?), რა
  ხდება რამდენიმე replica-ზე, სწორად ამოიცნობს თუ არა კლიენტს proxy-ს
  უკან (`ClientIpResolver`, `TRUSTED_PROXIES`).
- **ატვირთვები:** magic-byte შემოწმება, ზომის ლიმიტი, სახელის
  სანიტიზაცია, path traversal, ჩამოტვირთვისას ავტორიზაცია,
  `Content-Disposition`, XSS ატვირთული HTML/SVG-ით.
- **ინექციები:** SQL (native query, string concat), HTML/XSS (`innerHTML`,
  `[innerHTML]`, `bypassSecurityTrust*`, jsoup-ის sanitizer-ის კონფიგურაცია),
  CSV injection ექსპორტში (`=`, `+`, `-`, `@` უჯრის დასაწყისში).
- **CSRF / CORS / cookie:** `SameSite`, `Secure`, `HttpOnly`, CORS-ის
  allowlist, `*`-ის არსებობა.
- **Security headers:** CSP (და `docs/csp_nonce_refactor_plan.md`-ის
  სტატუსი), HSTS, `X-Content-Type-Options`, `X-Frame-Options`.
- **დამოკიდებულებები:** `requirements.txt`, `pom.xml`, `package-lock.json` —
  ცნობილი CVE-ები, მიტოვებული პაკეტები, ვერსიები, რომლებიც განზრახ
  არის ჩამორჩენილი (მაგ. `bcrypt==4.0.1`) — ეს ჩამორჩენა დღეს რისკია?
- **შეცდომების გაჟონვა:** stack trace, SQL-ის ტექსტი, შიდა hostname-ები
  კლიენტამდე ხომ არ მიდის (`GlobalExceptionHandler`, `/api/health`)?
