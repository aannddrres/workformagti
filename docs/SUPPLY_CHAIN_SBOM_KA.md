# მიწოდების ჯაჭვის უსაფრთხოება — SBOM და დაუცველობის სკანი

## რა არის ეს (მარტივად)

**SBOM** = „Software Bill of Materials" — პროგრამის **შემადგენლობის სია.**
ისევე, როგორც საკვების შეფუთვაზე ინგრედიენტების სია წერია, SBOM ჩამოთვლის
**ყველა გარე ბიბლიოთეკას**, რომელსაც პროექტი იყენებს, ზუსტი ვერსიით.

**რატომ სჭირდება IT-ს:** როცა მსოფლიოში ახალი დაუცველობა აღმოაჩინეს (მაგ.
2021-ის Log4Shell), პირველი კითხვა ყოველთვის ერთია — „ჩვენ ვიყენებთ ამ
ბიბლიოთეკას?". SBOM-ით პასუხი წამში მოდის, არა დღეებში. ამიტომ SBOM უკვე
**რეგულაციური მოთხოვნაა** (EU Cyber Resilience Act, US Executive Order
14028) და შესყიdვისას ხშირად პირდაპირ ითხოვენ.

## რა გვაქვს

| ნაწილი | ფაილი | ფორმატი |
|---|---|---|
| Backend (Java) | `java-backend/target/bom.json` | CycloneDX 1.5, ~126 კომპონენტი |
| Frontend (Angular) | `angular-frontend/bom.json` | CycloneDX 1.6, ~412 კომპონენტი |

CycloneDX არის ინდუსტრიის სტანდარტული, მანქანურ-წაკითხვადი ფორმატი —
პირდაპირ იტვირთება უსაფრთხოების ხელსაწყოებში.

## როგორ გენერირდება

- **Backend:** `cyclonedx-maven-plugin` მიბმულია `package`-ფაზაზე — `mvn
  package` თავისით ქმნის `target/bom.json`-ს. ცალკე: `mvn
  cyclonedx:makeAggregateBom`.
- **Frontend:** `npm run sbom` → `bom.json`.

ორივე ფაილი **build-არტეფაქტია** (gitignore-შია, კოდში არ ინახება) — ყოველ
build-ზე ახლიდან იქმნება, ესე იგი ყოველთვის მიმდინარეა.

## ავტომატური კარიბჭე (CI)

`.github/workflows/ci.yml`-ის **`supply-chain`** job ყოველ push/PR-ზე:

1. აგენერირებს ორივე SBOM-ს.
2. **Trivy**-ით ასკანერებს ბიბლიოთეკების SBOM-ებს და ორივე საბოლოო Docker
   image-ის ოპერაციული სისტემის პაკეტებს.
3. თუ იპოვა **HIGH ან CRITICAL** დონის, გამოსწორებადი დაუცველობა →
   **build ჩავარდება** (`--ignore-unfixed`: მხოლოდ ისეთი, რასაც ვერსიის
   განახლება ასწორებს, რომ კარიბჭე მოქმედებადი იყოს).
4. ორივე SBOM, image-სკანების JSON და image digest-ები იტვირთება
   **არტეფაქტად** (90 დღე) — IT-ს/შესყიდვას შეუძლია პირდაპირ ჩამოტვირთოს,
   build-ის გატეხვის შემთხვევაშიც.

## რას ავსებს

აქამდე:
- **Dependabot** (`.github/dependabot.yml`) — დროთა განმავლობაში ხსნის PR-ს
  დაუცველ დამოკიდებულებაზე (მუდმივი კონტროლი).
- **Frontend `npm audit`** კარიბჭე — moderate და უფრო მძიმე რჩევებს ამოწმებს
  როგორც გასაშვებ, ისე build-time ბიბლიოთეკებში.

აკლდა:
- **მანქანური SBOM** — ახლა არის (ორივე მხარისთვის).
- **Backend-ის „ახლა და აქ" შემოწმება** — Dependabot მოძრავია, ერთჯერად
  სურათს არ იძლეოდა; Trivy-სკანი ახლა იძლევა.

ეს ის „offline CVE-სკანის" ხარვეზი იყო, ადვერსარიულ რაუნდში რომ დაფიქსირდა.

## შენიშვნა

პირველ გაშვებაზე შესაძლოა Trivy-მ არსებული HIGH/CRITICAL იპოვოს რომელიმე
გარდამავალ დამოკიდებულებაში — ეს **კარიბჭის მუშაობაა, არა ხარვეზი.** მაშინ
გამოსავალი ორია: ბიბლიოთეკის განახლება, ან (თუ განახლება ჯერ არაა)
დროებითი, დათარიღებული გამონაკლისი დასაბუთებით.
