# მონაცემთა მიგრაცია: Postgres → Oracle (cutover ETL)

**სტატუსი:** ✅ **რეალურ Oracle-ზე გაშვებულია და მწვანეა** (Oracle XE 21c,
AL32UTF8, Flyway V42, 2026-08-23). გაზომილია production-ის მოდელირებულ
მოცულობაზეც: **2.65 მლნ სტრიქონი — 29 წთ 29 წმ**, შედარება სუფთა (§11.2).
CI-ში ავტომატიზებულია `etl-oracle` job-ით.
**კოდი:** `scripts/etl/`
**ტესტები:** `tests/etl/` — 89 ყველგან + 25 მხოლოდ Oracle-ზე (**114 მწვანე**)
**განახლებულია:** 2026-08-23

---

## 1. რატომ არსებობს ეს

დღემდე Oracle-ში მხოლოდ fixture/სატესტო მონაცემები გადადიოდა
(`docs/JAVA_ORACLE_ANGULAR_MIGRATION.md`). რეალური პორტალის ისტორია —
სტატიები, გაცნობის მტკიცებულებები, აუდიტის ჟურნალი, დანართები — ჯერ
არასდროს გადმოსულა, და cutover-ის მექანიზმი დოკუმენტში ერთი წინადადება იყო.

ეს პაკეტი სწორედ ამას აშენებს: **გეგმას, რომელიც თავად ამოწმებს თავს**.

## 2. ძირითადი პრინციპები

1. **ID-ები უცვლელი რჩება.** `article_view_logs`, read receipts,
   `required_readings`, აუდიტის ყოველი ჩანაწერი მასალას **id-ით** იხსენიებს.
   ახალი id-ების გამოცემა მტკიცებულებას გაწყვეტდა.
2. **ჩუმად არაფერი იკვეცება.** VARCHAR2-ის სიგანეზე გრძელი მნიშვნელობა
   preflight-ს **აჩერებს**, არ იჭრება.
3. **გამოგონილი მონაცემი არ იწერება.** სადაც წყაროში ფაქტი არ არის
   (`stored_files.uploaded_by`, AD-ის org ველები), რჩება `NULL`.
4. **ორი ცხრილის ბედი ინჟინრის გადასაწყვეტი არ არის** — იხ. §7.
5. **დამტკიცებული migration ხელახლა არ იწერება.** V36_1-ის MERGE
   კოპირებული არ არის — `load.py` მას თავად ფაილიდან კითხულობს.

## 4. გაშვების თანმიმდევრობა

```bash
# 0. დამოკიდებულებები
pip install -r requirements-dev.txt        # psycopg2 + oracledb

# 1. მშრალი რეპეტიცია — არაფერს წერს, მაგრამ ყველაფერს კითხულობს
python -m scripts.etl.cli preflight \
    --source "postgresql://appuser:***@db:5432/magti_portal" \
    --oracle-dsn "//oracle-host:1521/MAGTI" \
    --oracle-user MAGTI_PORTAL --oracle-password '***'

# 2. dry run — ტრანსფორმაცია და დათვლა, ჩაწერის გარეშე
python -m scripts.etl.cli load --dry-run  ...

# 3. რეალური დატვირთვა (change window-ში, Python read-only-ზე გადაყვანის შემდეგ)
python -m scripts.etl.cli all --uploads-dir /path/to/uploads  ...
```

ყოველი გაშვება წერს ორ ფაილს `reports/etl/`-ში: ქართულ Markdown-ს
change record-ისთვის და იმავე ფაქტების JSON-ს, რომ ორი რეპეტიცია
მექანიკურად შევადაროთ.

**რეპეტიცია რეალურ Oracle-ზე** (ისე, როგორც CI აკეთებს):

```bash
# 1. სქემა — Flyway-ით, ისევე როგორც production-ში
cd java-backend && mvn -B flyway:migrate \
    -Dflyway.url=jdbc:oracle:thin:@localhost:1521/XEPDB1 \
    -Dflyway.user=magti_app -Dflyway.password='***'

# 2. სრული რეპეტიცია + 25 Oracle-სპეციფიკური მტკიცება
ETL_ORACLE_DSN=localhost:1521/XEPDB1 \
ETL_ORACLE_USER=magti_app ETL_ORACLE_PASSWORD='***' \
    python -m pytest tests/etl -q
```

ეს ტესტები **მხოლოდ Oracle-ზე** მოწმდება (სხვაგან skip-დება) და სწორედ
იმას ამოწმებს, რაც სხვაგან არ არსებობს: IDENTITY იღებს მიგრირებულ id-ებს
და შემდეგ მათზე მაღლა აგრძელებს; V28-ის trigger ჰეშ-ჯაჭვს ზუსტად იმ
მნიშვნელობებით აღადგენს, რაც Postgres-ს ჰქონდა; 500-სიმბოლოიანი ქართული
სათაური `VARCHAR2(500 CHAR)`-ში ეტევა; 40 000-სიმბოლოიანი CLOB batch
bind-ს გადაურჩება; V36_1 დაკარგულ override-ს აღადგენს.

`mvn flyway:migrate` შესაძლებელი გახდა `flyway-maven-plugin`-ის დამატებით
(`java-backend/pom.xml`) — აპლიკაციის ქცევა უცვლელია, უბრალოდ სქემის
გაშვება აღარ საჭიროებს აპლიკაციის აწევას (იგივე, რაც DBA-ს სჭირდება
cutover-ზე).

**რეპეტიცია Oracle-ის გარეშე:**

```bash
python -m scripts.etl.cli all --source sqlite:///magti_portal.db \
    --rehearsal-target /tmp/rehearsal.db --skip-uploads
```

ეს ამოწმებს გეგმას, თანმიმდევრობასა და შედარების ლოგიკას — **და მხოლოდ
ამას**. IDENTITY, V28-ის trigger და VARCHAR2-ის სიგანე იქ არ არსებობს, და
ანგარიშიც ყოველ ჯერზე ამას წერს.

## 5. ID-ების შენარჩუნება — რატომ არის ეს ცალკე თემა

Oracle-ის სქემაში **ყველა** ცხრილი `GENERATED ALWAYS AS IDENTITY`-ია, რაც
პირდაპირ id-ს **კრძალავს** (ORA-32795). ამიტომ:

```
ALTER TABLE t MODIFY (id GENERATED BY DEFAULT AS IDENTITY)     -- დატვირთვამდე
...
ALTER TABLE t MODIFY (id GENERATED ALWAYS AS IDENTITY (START WITH LIMIT VALUE))
```

`START WITH LIMIT VALUE` თანმიმდევრობას `max(id)+1`-ზე აყენებს — cutover-ის
შემდეგ აპლიკაციის პირველი ჩანაწერი მიგრირებულს **ვერ დაეჯახება**.
`reconcile.py` ამას ცალკე ამოწმებს (`user_sequences.last_number` vs `MAX(id)`).

> ⚠️ ეს ნიშნავს, რომ ETL-ს **`ALTER TABLE` უფლება სჭირდება** სქემაზე.
> იხ. `QUESTIONS_FOR_IT.md` §12.

## 6. ორი ხაფანგი, რომელიც უკვე დაჭერილია

**ა) V36_1 ცარიელ ცხრილზე გაეშვა.**
`V36_1__legacy_permission_override_backfill.sql` კითხულობს `users.permissions`-ს
და თითოეულ ხელით მინიჭებულ უფლებას ცალსახა `ALLOW`/`DENY` override-ად აქცევს.
Flyway მას **მიგრაციის დროს** უშვებს — ანუ ცარიელ `users`-ზე, ETL-მდე დიდი
ხნით ადრე. თუ ხელახლა არ გაეშვა, ყოველი მიგრირებული მომხმარებელი ჩუმად
როლის დეფოლტ უფლებებზე დაბრუნდებოდა: ვისაც ხელით ჰქონდა მინიჭებული ან
ჩამორთმეული უფლება, cutover-ის შემდეგ სხვა წვდომას მიიღებდა.
`load.py` ამ MERGE-ს **თავად migration-ის ფაილიდან კითხულობს** და ხელახლა
უშვებს; `WHEN NOT MATCHED` მას იდემპოტენტურს ხდის.

**ბ) აუდიტის ჯაჭვი — მიგრაციის ყველაზე ძლიერი მტკიცებულება.**
V28-ის `BEFORE INSERT` trigger ჰეშ-ჯაჭვს **თავად ხელახლა აშენებს** იმავე
canonical string-იდან, რომელსაც Postgres-ის trigger იყენებდა. ამიტომ:

- `prev_hash`/`row_hash` **არ იწერება** — trigger-ის საკუთრებაა;
- `audit_logs` იტვირთება **ერთ ნაკადად, id-ის ზრდადობით**;
- შემდეგ `reconcile.py` **row-по-row ადარებს Postgres-ის `row_hash`-ს
  Oracle-ის დათვლილს.**

თუ თუნდაც ერთი აუდიტირებული ველი გზაში შეიცვალა (კოდირება, დროის ზონა,
CLOB-ის კიდე), ჰეშები **სწორედ იმ სტრიქონიდან განსხვავდება**. ეს არის
ერთადერთი შემოწმება, რომელიც არა უბრალოდ „დათვალა", არამედ **ამტკიცებს**.

**ორი პირობა, რომლის გარეშეც ეს შედარება არ მუშაობს:**

1. სამიზნის ჯაჭვი genesis-ზე უნდა იდგეს (ცარიელი `audit_logs`), თორემ
   `prev_hash` სხვა წერტილიდან იწყება;
2. წყაროს ჯაჭვი **სრული უნდა იყოს**. Postgres tip-ს ისე ირჩევს, რომ
   `row_hash IS NULL` სტრიქონებს **გამოტოვებს** (trigger-ამდე დაწერილი
   ჩანაწერები), Oracle კი ყველა სტრიქონს ჰეშავს. ერთი ასეთი სტრიქონიც
   საკმარისია, რომ ორი ჯაჭვი იქიდან **კანონიერად** დაშორდეს.
   ამიტომ `reconcile.py` ასეთ შემთხვევაში პირდაპირ შედარებას **არ**
   ასრულებს და ამას ღიად წერს — false mismatch-ების ზვავის ნაცვლად.

მეორე შემთხვევისთვის არსებობს დამოუკიდებელი მტკიცებულება: `audit_chain.py`
canonical string-ის **მესამე იმპლემენტაციაა** (Python-ში), რომლითაც
`verify_target_chain()` Oracle-ის ყოველ მიგრირებულ სტრიქონს **ხელახლა
ჰეშავს იმ მნიშვნელობებიდან, რაც Oracle-მა დააბრუნა** და ჯაჭვის კავშირსაც
ამოწმებს. ეს მუშაობს მაშინაც, როცა პირდაპირი შედარება გამოუსადეგარია.

## 8. დანართები

Python-ი ფაილებს pod-ის დისკზე წერდა, Java მათ Oracle-ში ინახავს
(`stored_files`, V31 — audit PR-03). ამიტომ `uploads.py` **დირექტორიას
კითხულობს**, არა ცხრილს, და ორ სხვადასხვა პრობლემას ცალკე ანგარიშობს:

- **მითითებულია, მაგრამ დისკზე არ არის** — ეს pod-ის გადატვირთვის ძველი
  ბაგის მემკვიდრეობაა (უკვე 404-ია დღესაც), არა მიგრაციის დაზიანება;
- **დისკზეა, მაგრამ ბმული აღარ არსებობს** — მაინც გადმოგვაქვს; წაშლა
  retention-ის გადაწყვეტილებაა.

`uploaded_by` რჩება `NULL` — ფაილურ სისტემას ატვირთვის ავტორი არ ახსოვს,
და სტატიის ავტორის „მიწერა" მტკიცებულების ცხრილში გამოგონილი ფაქტი იქნებოდა.

| სვეტი | რას ნიშნავს |

| წყარო / სამიზნე | სტრიქონების რაოდენობა ორივე მხარეს |
| განსხვავებული | ერთი და იმავე id-ის სტრიქონი, რომლის **შიგთავსი** არ ემთხვევა |

`canon()` განზრახ ათანაბრებს სამ რამეს: `''` და `NULL` (Oracle-ის
სემანტიკა — ცალკე preflight-ის გაფრთხილება ითვლის, რამდენი ასეთია),
datetime-ს და timestamp-ის ტექსტს, და რიცხვის ჩაწერის ფორმებს.

## 10. Rollback

ETL-ს **უკუქცევა არ სჭირდება**: ის მხოლოდ Oracle-ში წერს, წყაროს ხელს არ
ახლებს (Postgres-ის სესია `READ ONLY`-ია). ჩავარდნის შემთხვევაში rollback
არის „Oracle-ის სქემის თავიდან შექმნა Flyway-ით და ხელახლა გაშვება" —
სწორედ ამიტომ მოითხოვს preflight ცარიელ სამიზნეს.

## 11.1. რა იპოვა პირველმა რეალურმა Oracle-გაშვებამ

სამივე დეფექტი **მხოლოდ Oracle-ზე** ჩანდა; SQLite-რეპეტიცია სამივეზე მწვანე იყო.

| # | პრობლემა | რატომ არ ჩანდა ადრე |
|---|---|---|
| 1 | `flyway_schema_history`-ის სვეტები Flyway-მ **ბრჭყალებში, პატარა ასოებით** შექმნა — `success`/`version` ბრჭყალების გარეშე ვერ იძებნება (ORA-00904) | SQLite-ს Flyway-ის ისტორიის ცხრილი არ აქვს |
| 2 | `reconcile` `id`-ს **ორჯერ** ირჩევდა select-ში (გასაღები + fingerprint) — Oracle ამას `ORDER BY`-სთან ერთად აგდებს (ORA-00960) | SQLite დუბლირებულ სვეტს ჩუმად იღებს |
| 3 | ანგარიშის რენდერი `KeyError: 'status'`-ით ვარდებოდა, როცა თუნდაც ერთი შემოწმება არ იყო მწვანე (`status` property-ია, `asdict()` მას ტოვებს) | ყველა წინა გაშვება სრულიად მწვანე იყო — ეს ტოტი არასდროს შესრულებულა |

დამატებით დაფიქსირდა (დეფექტი არა, ქცევის სხვაობა): Oracle **21c**-ზე
python-oracledb `CHECK (... IS JSON)`-იან CLOB-ს **უკვე გაშიფრულ Python-სიად**
აბრუნებს, 19c-ზე კი ტექსტად. `reconcile` ორივე მხარეს ერთ კანონიკურ JSON-ფორმაზე
დაჰყავს — თორემ იგივე მონაცემი ერთ ვერსიაზე „დაზიანებულად" ჩაითვლებოდა, მეორეზე კი არა.

სამივეზე დაემატა regression-ტესტი, რომელიც **Oracle-ის გარეშეც** ვარდება.

### როგორ გამოვთვალოთ თქვენი რეალური ფანჯარა

```

     + (დანართების_MB / 21)
```

production-იდან: `QUESTIONS_FOR_IT.md` §12.3-ში მზა SQL-ია.
