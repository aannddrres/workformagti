# Magti Portal — UI/UX განვითარების გეგმა

**სტატუსი:** ეტაპობრივი დანერგვა ავტორიზებულია — ფაზა 1/2-ის პირველი სამუშაო ჭრილი აშენებულია
**ბოლო განახლება:** 2026-08-21
**მოთხოვნების წყარო:** `docs/PRODUCT_UX_REQUIREMENTS_KA.md`

ეს გეგმა აღწერს პორტალის მიზნობრივ გამოცდილებას, ინფორმაციულ არქიტექტურას,
სისტემური ადმინის ეკრანებს, საერთო დიზაინ-სისტემას, სხვა როლების გარემოსა და
ეტაპობრივ დანერგვას. გეგმა ეყრდნობა მიმდინარე Angular UI-ის, Java/Oracle
backend-ისა და რეალური ადგილობრივი მონაცემების ინვენტარიზაციას.

## 1. დიზაინის მთავარი გადაწყვეტილება

პორტალი უნდა გახდეს **როლზე მორგებული საოპერაციო ცოდნის ცენტრი** და არა
მარკეტინგული საიტი ან ერთმანეთისგან იზოლირებული CRUD გვერდების ნაკრები.

სისტემის სამი მთავარი თვისებაა:

1. **სისწრაფე** — ოპერატორი შესაბამის სტატიას 1–2 წამში პოულობს;
2. **სანდოობა** — ყველა ოფიციალური გაცნობა მიბმულია ზუსტ ვერსიაზე;
3. **მართვადობა** — სისტემური ადმინი ფიქსირებული role catalog-იდან ძირითად
   როლს, არსებულ permissions-სა და scope-ებს UI-დან მართავს კოდში ჩარევის გარეშე.

UI-ის ყველა გადაწყვეტილება უნდა პასუხობდეს ერთ კითხვას: „რომელია ამ
მომხმარებლის შემდეგი ყველაზე მნიშვნელოვანი მოქმედება?“

## 2. მიმდინარე მდგომარეობის UX შეფასება

### ძლიერი საფუძველი

- გლობალური ძებნა ყველა გვერდის ზედა ზოლში უკვე არსებობს;
- light/dark theme-ის საფუძველი შექმნილია;
- ადმინისტრაციული statistics, content, users, roles, categories და audit
  გვერდები ფუნქციურად არსებობს;
- audit-ს აქვს ფილტრები, დეტალების გვერდითი panel და hash-chain integrity;
- content editor-ს აქვს article/news/video სამუშაო პროცესები;
- permission-ების ხელით მინიჭების endpoint და UI-ის ნაწილი უკვე არსებობს.

### ძირითადი UX პრობლემები

- „მთავარი“ გვერდი სტატისტიკურ ანგარიშს ჰგავს და არა ყოველდღიურ სამუშაო
  საწყის წერტილს;
- სისტემური ადმინიც ვერ ხედავს მთავარზე მისთვის ხელმისაწვდომ კატეგორიებს;
- „მომხმარებლები“ და „როლების მართვა“ ერთსა და იმავე პასუხისმგებლობას ორ
  ადგილას ანაწილებს;
- sidebar-ში სამუშაო და ადმინისტრაციული ფუნქციები ვიზუალურად ზედმეტად
  თანაბარი წონითაა წარმოდგენილი;
- content table აჩვენებს მხოლოდ სათაურს, კატეგორიას, თარიღსა და მოქმედებას;
  არ ჩანს პასუხისმგებელი, აუდიტორია, lifecycle, review ან compliance;
- category table ბრტყელია და იერარქიას მხოლოდ ტექსტით მიანიშნებს;
- profile/personal cabinet ფაქტობრივად placeholder-ია;
- პორტალში ჯერ კიდევ არსებობს პირადი messaging flow, რომელიც დადასტურებული
  scope-იდან ამოღებულია;
- ქართული UI-ის მიუხედავად, audit action-ები და რამდენიმე დეპარტამენტი
  ინგლისურად ჩანს; თარიღის ნაწილი ამერიკულ ფორმატს იყენებს;
- ბრენდ-ფერი უკვე ერთ ცენტრალიზებულ token-შია მოქცეული, მაგრამ ზუსტი მნიშვნელობა
  ოფიციალური brand book-ის მიღებამდე provisional-ია; ქართული შრიფტი self-hosted
  არ არის.

### მოთხოვნებთან ტექნიკური შეუსაბამობები

| მოთხოვნა | მიმდინარე მდგომარეობა | საჭირო ცვლილება |
|---|---|---|
| პასუხისმგებლობების შეთავსება | `users.role` + per-user permissions უკვე არსებობს | ჯერ capability-gap ტესტი; `user_roles` მხოლოდ დამტკიცებული საჭიროების შემთხვევაში |
| დეპარტამენტი/ჯგუფი/უფროსი | free-text `department`; `teams`, `team_id`, `manager_id` რეალურ მონაცემებში გამოუყენებელია | ნორმალიზებული AD-owned org structure + ადგილობრივი leadership assignment; იხ. `ORG_ACCESS_ARCHITECTURE_PLAN_KA.md` |
| რამდენიმე კატეგორია სტატიაზე | `articles.category_id` ერთია | `article_categories` many-to-many კავშირი |
| typo/transliteration search | exact substring + ყველა trigram-ის თანხვედრა | fuzzy ranking, normalisation და transliteration index |
| მნიშვნელოვანი და მცირე ვერსიები | history/version არსებობს, მაგრამ ორი დონე არა | revision + compliance release მოდელი |
| ხელახალი გაცნობა მნიშვნელოვან edit-ზე | ავტომატური release obligation არ არის | ახალი compliance version და ახალი assignment |
| ფართო აუდიტორია | article-ს რამდენიმე department აქვს; reading/broadcast-ს ძირითადად ერთი | საერთო audience targeting მოდელი |
| სრული Broadcast lifecycle | არსებული broadcast შეზღუდულია და personal messages-თანაა შერეული | დამოუკიდებელი persistent Broadcast მოდული |
| 3-თვიანი review + override | `last_verified_at` არსებობს | global default, per-item interval და scheduler |
| profile/cabinet | placeholder routes | საერთო account shell და role summaries |
| 100–200% font scaling | არ არსებობს | preference + reflow-safe component სისტემა |
| ციფრული category slug | category view ციფრულ route-ს ჯერ ID-ად კითხულობს | slug/ID namespace-ის ცალსახა წესი redesign-მდე |
| slug uniqueness | application-level შემოწმებას DB unique constraint არ იცავს | concurrency-safe uniqueness design და არსებული duplicate-ების cleanup გადაწყვეტილება |

ეს ცვლილებები redesign-ის ნაწილია და არა მომავალში გადასადები „დამატებები“;
მათ გარეშე შეთანხმებული UX ზუსტად ვერ იმუშავებს.

## 3. მიზნობრივი ინფორმაციული არქიტექტურა

### საერთო ნავიგაცია

**სამუშაო**

- მთავარი;
- ცოდნის ბაზა;
- სავალდებულო გაცნობა;
- სიახლეები;
- ვიდეო ინსტრუქციები;
- რჩეულები.

**გუნდი** — მხოლოდ შესაბამისი უფლებით

- გუნდის მდგომარეობა;
- გაცნობის კონტროლი;
- ანგარიშები.

**ადმინისტრირება** — permission-ის მიხედვით

- მიმოხილვა;
- კონტენტი;
- კატეგორიები;
- მომხმარებლები და წვდომა;
- გაცნობის ადმინისტრირება;
- Broadcast;
- აუდიტი და უსაფრთხოება;
- სისტემის პარამეტრები.

**პირადი სივრცე**

- პირადი კაბინეტი იხსნება topbar-ის account menu-დან და არა როგორც კიდევ
  ერთი თანაბარი სამუშაო მოდული sidebar-ში.

### დუბლირების გაუქმება

- `მომხმარებლები` და `როლების მართვა` ერთიანდება `მომხმარებლები და წვდომა`
  სივრცეში;
- მთავარი აჩვენებს მხოლოდ summary-ს და deep link-ს, არა სრულ ცხრილს;
- პირადი კაბინეტი აჩვენებს მხოლოდ კონკრეტული ადამიანის summary-ს;
- compliance-ის სრული ადმინისტრირება ცხოვრობს ერთ გვერდზე;
- Broadcast არ მეორდება პირად შეტყობინებებში;
- სტატისტიკა თითოეული domain-ის შესაბამის გვერდზე drill-down-ით იხსნება.

## 4. საერთო App Shell

### Sidebar

- desktop სიგანე: დაახლოებით 248–264px;
- დაჯგუფებული სექციები მკაფიო სათაურებით;
- აქტიური გვერდი აღინიშნება Magti red ხაზით და მსუბუქი ფონით;
- მხოლოდ რეალურად დაშვებული ბმულები ჩანს;
- დამატებითი permission-ით დაშვებული ფუნქცია მხოლოდ ერთხელ ჩანს;
- collapse რეჟიმი შეიძლება დაემატოს 1280px-მდე სამუშაო სივრცის გასაზრდელად.

### Topbar

- ცენტრში/მარცხნივ — ფართო გლობალური ძებნა;
- მარჯვნივ — notification center, font-size, theme და account menu;
- ენის გადამრთველი ამოიღება, რადგან პროდუქტის ენა მხოლოდ ქართულია;
- logout account menu-ში გადავა;
- გვერდის title/breadcrumb მოკლე და ერთმნიშვნელოვანი იქნება.

### Content canvas

- ფართო desktop layout, მაქსიმუმ დაახლოებით 1600px სამუშაო სიგანე;
- 1080p full-screen გარემო პირველადი სამიზნეა;
- 1280px-დან ultrawide-მდე layout არ უნდა კარგავდეს hierarchy-ს;
- 200% font mode-ზე კომპონენტები გადალაგდება და მოქმედებები არ დაიფარება;
- fixed-width modal-ის ნაცვლად რთული ადმინისტრაციული ფორმები drawer ან full
  page workspace-ში გაიხსნება.

## 5. სისტემური ადმინის მთავარი — `/admin/overview`

მთავარი აღარ იქნება მხოლოდ chart-ების კოლექცია. მისი რიგია:

### 5.1. სათაური და სწრაფი მოქმედებები

- „სისტემის მიმოხილვა“;
- ბოლო განახლების დრო;
- `ახალი მომხმარებელი`, `ახალი სტატია`, `Broadcast`, `აუდიტის გახსნა`.

### 5.2. ყურადღებას საჭიროებს

პირველ ეკრანზე გამოჩნდება მხოლოდ actionable ინფორმაცია:

- ვადაგადაცილებული გაცნობები;
- უსაფრთხოების კრიტიკული მოვლენები;
- გადასამოწმებელი სტატიები;
- მალე დასამალი/ვადაგასული კონტენტი;
- უშედეგო ძიებების რაოდენობა.

თითოეული card კლიკით გახსნის უკვე გაფილტრულ კანონიკურ გვერდს.

### 5.3. კატეგორიები

- მომხმარებლისთვის დაშვებული ძირითადი კატეგორიების grid;
- მასალების რაოდენობა და ბოლო განახლების თარიღი;
- კლიკი გადადის knowledge base-ის შესაბამის category view-ზე;
- admin ფუნქციები category card-ში არ აირევა — რედაქტირება ცალკე taxonomy
  გვერდზე დარჩება.

### 5.4. სისტემის მოკლე მდგომარეობა

- აქტიური/გათიშული მომხმარებლები;
- პუბლიკაციები და აქტიური სავალდებულო მასალები;
- მიმდინარე Broadcast-ები;
- audit chain health;
- backend/search status მხოლოდ მაშინ გამოჩნდება, როცა რეალური პრობლემა აქვს.

### 5.5. ანალიტიკა

- ძიების წარმატება/უშედეგობა;
- compliance trend;
- აქტივობის trend;
- chart-ები მეორე/მესამე დონეზეა, action-needed ბლოკების შემდეგ.

## 6. მომხმარებლები და წვდომა — `/admin/access`

ეს ხდება მომხმარებლებისა და უფლებების ერთადერთი კანონიკური სივრცე.

### 6.1. ჩანართები

- `მომხმარებლები`;
- `როლები და უფლებები` — ოთხი ფიქსირებული როლის კატალოგი;
- `წვდომის ცვლილებების ისტორია` — audit-ის მზა ფილტრი.

### 6.2. მომხმარებლების ცხრილი

ნაგულისხმევად ხილული სვეტები:

- checkbox;
- სახელი და კორპორაციული ელფოსტა;
- დეპარტამენტი / ჯგუფი;
- ძირითადი როლი;
- სტატუსი;
- ვადაგადაცილებული ვალდებულებები;
- ბოლო შესვლა;

  რეალური enforcement და UI ერთ მოდელს უნდა იყენებდეს.
- თუ მომავალში multi-role-ს ცალკე საჭიროება დადასტურდა: permissions არის

## 19. Acceptance criteria

### საერთო

- Chrome/1080p-ზე ყველა primary action პირველადი scroll-ის ფარგლებშია;
- 1280px–ultrawide და 100–200% font mode-ზე მოქმედება არ იჭრება;
- untranslated key, ინგლისური business label და US date format არ რჩება;
- keyboard focus და contrast WCAG 2.2 AA მოთხოვნას აკმაყოფილებს;
- ერთი ფუნქციის მხოლოდ ერთი canonical workflow არსებობს.

### ძებნა

- P95 პასუხი <2 წამი 150 concurrent user დატვირთვაზე;
- შეთანხმებული test corpus-ის 1–2 typo და transposition შემთხვევები პოულობს
  სწორ სტატიას;
- ლათინური ტრანსლიტერაცია პოულობს შესაბამის ქართულ ტერმინს;
- exact title ყოველთვის body-only დამთხვევაზე მაღლა დგას;
- visibility filter არასოდეს აბრუნებს დაუშვებელ კონტენტს.

### სტატიის კითხვა და გადმოტანილი კონტენტი

- შენახული legacy HTML არ იცვლება; renderer-ის ჩართვამდე და შემდეგ ტექსტის
  სიმბოლოები და მათი თანმიმდევრობა ავტომატური invariant test-ით ემთხვევა;
- Chrome/1080p-ზე ძირითადი ტექსტის სვეტი ინარჩუნებს წაკითხვად სიგანეს,
  აბზაცებს აქვს მკაფიო რიტმი, ხოლო არსებული სიები, სათაურები, ცხრილები,
  სურათები და ტექნიკური კოდები ვიზუალურად გასარჩევია;
- renderer არ ქმნის ახალ სათაურებს, არ ყოფს/აერთიანებს წინადადებებს და არ
  ცვლის მართლწერას; ასეთი ცვლილება მხოლოდ ცალკე კონტენტ-რედაქტირების
  გადაწყვეტილებით არის შესაძლებელი;
- parent category აჩვენებს child category-ებსა და recursive total-ს; ცარიელი
  parent view დაუშვებელია, როცა შვილებში მომხმარებლისთვის ხილული მასალაა;
- ყველა კანონიკური სტატია pagination/„მეტის ჩატვირთვით“ მისაწვდომია და E2E/
  სატესტო ჩანაწერები ოპერატორის კატალოგსა და ძებნაში არ ჩნდება;
- ძველი შიდა Google Sites ბმული ცნობილ შესაბამისობაზე პორტალის article route-ზე
  იხსნება, ხოლო უცნობი შესაბამისობა მკაფიოდ აღინიშნება და არ იკარგება ჩუმად.

### წვდომა

- ერთი ძირითადი role + per-user permissions პასუხისმგებლობების შეთანხმებულ
  მაგალითებს ფარავს;
- permission ცვლილება ახალ მოთხოვნაზე დაუყოვნებლივ მოქმედებს;
- UI-ის effective-access preview backend enforcement-ს ემთხვევა;
- ბოლო სისტემური ადმინის დაცვა ყველა single/bulk გზაზე მუშაობს;
- ყოველი privileged ცვლილება audit-ში ჩანს.

### Retention და მტკიცებულება

- Java backend-ში დაუმტკიცებელი ავტომატური purge არ მუშაობს;
- quiz attempts, read receipts/acknowledgments და compliance evidence არასოდეს
  ხვდება ზოგად audit/view-log purge-ში;
- `audit_logs` და `article_view_logs`-ის ზრდას აქვს monitoring, capacity და
  დამტკიცებული archive/retention გეგმა production-მდე.

### ვერსია და compliance

- ყველა save revision-ია;
- მნიშვნელოვანი edit ახალი compliance version-ია;
- ძველი acknowledgment ისტორიულად რჩება, ახალი ვერსია ახალ ვალდებულებას
  ქმნის;
- quiz audit ინახავს ყველა მცდელობასა და ზუსტ question/version snapshot-ს;
- manager მხოლოდ საკუთარ scope-ს ხედავს და export-ავს.

### Broadcast

- აუდიტორია ყოველთვის ყველა ავტორიზებული თანამშრომელია;
- პირადი message/reply UI არ არსებობს;
- banner მომხმარებლის მიერ არ იხურება, მაგრამ არ ბლოკავს პორტალის გამოყენებას;
- ჩანს მთავარ გვერდსა და პროფილში და გამომქვეყნებელს შეუძლია დროზე ადრე მოხსნა;
- Broadcast სრულად აუდიტირდება.

## 20. გარე დასადასტურებელი საკითხები

გეგმის დაწყებას არ ბლოკავს, მაგრამ production-მდე საჭიროა:

- ოფიციალური Magti brand colors, logo asset და ქართული font;
- იურიდიული/DPO დადასტურება acknowledgment/quiz მტკიცებულების შენახვის ვადაზე;
- ხელმძღვანელის ფიქსირებული რვასვეტიანი export-ის DPO/იურიდიული validation და
  SYSTEM_ADMIN-only სრული log-export-ის Security/DPO validation;
- audit/export retention-ის production policy.

## 21. გადაწყვეტილება ამ ეტაპზე

მომხმარებელმა 2026-08-21 დაადასტურა ეტაპობრივი დანერგვა და სისტემური ადმინიდან
დაწყება. წვდომის მოდელი არის **ერთი ძირითადი role + დამატებითი per-user
permissions**; custom role და multi-role migration ამ ეტაპზე არ იგეგმება.

მომზადდა და რეალურ Angular გარემოში დაინერგა სისტემური ადმინის ოთხი ძირითადი
მიმართულების პირველი სამუშაო ჭრილი:

1. სისტემის მიმოხილვა;
2. მომხმარებლები და წვდომა;
3. მომხმარებლის detail drawer;
4. კონტენტის მართვის არსებული table/editor shell-ის აუდიტი და ერთიან
   დიზაინ-სისტემასთან თავსებადობა.

შემდეგი ფაზების განხორციელება მიჰყვება §18-ს. Backend-ის გარეშე საჭირო
შესაძლებლობები არ უნდა გამოისახოს როგორც მოქმედი UI.
