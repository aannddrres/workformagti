## მოთხოვნილი დოკუმენტის სტრუქტურა (4 სექცია)

### სექცია 1 — ფაზური მიგრაციის არქიტექტურული გეგმა
- **Big-Bang მიგრაციის თავიდან აცილება.** რეკომენდებული მიდგომა: ჯერ
  Backend + DB (Java + Oracle) გადადის იმავე REST API კონტრაქტის მიღმა —
  არსებული ვანილა-JS ფრონტენდი უცვლელად აგრძელებს მუშაობას ახალი backend-ის
  წინააღმდეგ. მხოლოდ ამის დამოწმების შემდეგ იწყება Angular-ზე გადასვლა, როგორც
  ცალკე ფაზა.
- დაასაბუთე, რატომ ეს თანმიმდევრობა (და არა პარალელური/ერთდროული სამივე
  ფენის შეცვლა).
- ჩაშალე თითოეული ფაზა ქვე-ნაბიჯებად, რისკის მიხედვით დალაგებული (უსაფრთხოებასთან
  დაკავშირებული კომპონენტები — პირველ რიგში).

### სექცია 2 — ტექნიკური რისკებისა და ტრანსლაციის მატრიცა
სამი ცხრილი (მიმდინარე მექანიზმი → სამიზნე მექანიზმი → კონკრეტული რისკი →
შერბილების სტრატეგია):

1. **PostgreSQL → Oracle** — მათ შორის: `audit_logs`-ის BEFORE INSERT
   ტრიგერი (გაყალბებისგან დაცული ჰეშ-ჯაჭვი, იყენებს
   `pg_advisory_xact_lock`-ს და `pgcrypto.digest()`-ს) → Oracle-ის PL/SQL
   ეკვივალენტი (`DBMS_LOCK`/lock-ცხრილი, `DBMS_CRYPTO.HASH`,
   `DBMS_SESSION.SET_CONTEXT`); `pg_trgm` + GIN ტრიგრამული ინდექსები
   (ძებნისთვის) → Oracle Text (განსხვავებული ტექნოლოგია, საჭიროებს
   ცალკე tuning-ს); `JSON` ტიპის სვეტები (დაადასტურე, Oracle-ის რომელი
   ვერსია გვაქვს — 12c-ის CLOB-ხრიკი vs 21c+-ის native მხარდაჭერა
   არსებითად განსხვავებულია); ცარიელი სტრიქონის vs `NULL`-ის დამუშავების
   განსხვავება Oracle-სა და Postgres-ს შორის.
2. **Python/FastAPI → Java/Spring Boot** — მათ შორის: SQLAlchemy-ის
   ORM-დონის auto-audit listener (ერთი გენერიკული მექანიზმი, გაზიარებული
   6 Entity-კლასზე, diff-ის გამოთვლა attribute-history introspection-ით)
   → Hibernate Envers ან custom `@EntityListeners` (სტრუქტურულად
   განსხვავებული მოდელი — საჭიროა შეგნებული არქიტექტურული გადაწყვეტილება,
   არა მექანიკური პორტი); bcrypt ჰეშების პორტირებადობა (კარგი ამბავი —
   Spring Security-ის `BCryptPasswordEncoder`-ს შეუძლია არსებული ჰეშების
   გადამოწმება, პაროლის იძულებითი აღდგენა არ სჭირდება); Redis-ზე
   დაფუძნებული SSE broker-ის sync/async ბიძგი (`asyncio.run_coroutine_
   threadsafe`) → Spring WebFlux-ის `Sinks`/reactive SSE ან `SseEmitter`
   რეესტრი; ქართული გლიფების PDF გენერაცია (reportlab + DejaVu Sans) →
   iText/PDFBox იმავე შრიფტის ხელახლა ჩაშენებით; rate-limiting (slowapi)
   → Bucket4j/Resilience4j (განსხვავებული ინტეგრაციის წერტილი).
3. **Vanilla JS → Angular** — მათ შორის: ინკრემენტული მიგრაციის გზა არ
   არსებობს (დაადასტურე მიმდინარე რაოდენობები: `window`-ზე გატანილი
   გლობალური ფუნქციები, inline `onclick=` ატრიბუტები, `innerHTML`
   სტრიქონული შაბლონები); მხოლოდ მცირე ნაწილი `fetch()` გამოძახებებისა
   გადის ერთიან wrapper-ში — დანარჩენი საჭიროებს ხელით გადამოწმებას
   Angular-ის service-ფენაზე გადატანისას; მესამე მხარის ბიბლიოთეკებს
   (rich-text რედაქტორი, charting) ჰყავთ Angular wrapper-ები, ხოლო
   ხელნაკეთ SVG-დაშბორდებს — არა (სრული ხელახალი წერა); დღეს არ არსებობს
   build-პროცესი, Angular კი მას ითხოვს.

### სექცია 3 — გადამოწმებისა და ტესტირების ჩარჩო (Verification Protocol)
- **API Parity Testing** — ავტომატური diff-ტესტირების მექანიზმი (მაგ.
  pytest + httpx, ან Postman/Newman კოლექცია), რომელიც იმავე მოთხოვნას
  უგზავნის ძველ (FastAPI) და ახალ (Spring Boot) სერვერს პარალელურად და
  ადარებს პასუხის სტრუქტურას, მნიშვნელობებს, HTTP სტატუსს და მნიშვნელოვან
  header-ებს. ორივე backend უნდა იყოს დათესლილი იდენტური fixture-მონაცემებით
  (გამოიყენე არსებული ტესტ-ფაბრიკების ლოგიკა, თუ ეს არსებობს რეპოში).
  **ცნობილი, განზრახ განსხვავებები (იხ. ქვემოთ) წინასწარ უნდა იყოს
  allowlist-ში**, რომ diff-ტესტმა ცრუ-negative არ დააფიქსიროს უკვე ცნობილ
  და გადაწყვეტილ ქცევებზე.
- **მონაცემთა და უსაფრთხოების მთლიანობა** — (ა) bcrypt ჰეშების რეალური
  გადამოწმება ყველა მომხმარებლისთვის, პაროლის იძულებითი აღდგენის გარეშე;
  (ბ) აუდიტის ჰეშ-ჯაჭვის მთლიანობის ტესტირება ახალ (Oracle-ზე დაფუძნებულ)
  მექანიზმზე — გაიმეორე იგივე scenario-ები, რასაც ამჟამინდელი
  `verify`/`chain-health` endpoint-ები ამოწმებენ (შეცვლილი წინა ჩანაწერი,
  ყალბი "წარმოშობის" ჩანაწერი შუაში); (გ) ქართული ტექსტის მთლიანობა —
  ძებნის რელევანტურობის შედარება (pg_trgm-ის ტოპ-N შედეგები vs Oracle
  Text-ის) და PDF-ის ვიზუალური შედარება (იგივე input, ორივე ძრავაზე).
- **ცნობილი შეუსაბამობების რეგრესია** — დეპარტამენტის შესატყვისობის
  ლოგიკის სამი განსხვავებული წესი (იხ. ქვემოთ, პუნქტი 6) უნდა დარჩეს
  შეგნებული გადაწყვეტილების შედეგი, არა შემთხვევითი გაერთიანება/გახლეჩვა.

### სექცია 4 — ფუნქციური გადამოწმების დეტალური მატრიცა
სრული ცხრილი, სვეტებით: **მოდული | კონკრეტული ფუნქცია/ბიზნეს-ლოგიკა |
API endpoint / UI კომპონენტი | ტესტირების მეთოდი | მიღების კრიტერიუმი**.
დაალაგე დომენების მიხედვით (Auth/Identity, Content/Articles-News-Videos,
Compliance, Stats/Reporting, Audit/Messaging). ერთი მწკრივი თითო
endpoint-ზე, რომელსაც აქვს არატრივიალური ბიზნეს-ლოგიკა; მარტივი,
გამეორებადი read-only endpoint-ები დააჯგუფე ერთ შემაჯამებელ მწკრივში,
რომ ცხრილი დარჩეს რეალურად გამოსაყენებელი და არა ხელოვნურად გაბერილი.

## ცნობილი ხარვეზები, რომლებიც მიგრაციასთან ერთად უნდა გასწორდეს

ეს არის წინა სესიაში აღმოჩენილი, კონკრეტული, დადასტურებული ხარვეზები —
**ჯერ დაადასტურე თითოეული რეალურ კოდში**, შემდეგ გადაწყვიტე თითოეულისთვის
ცალკე: გასწორება მიგრაციისას, თუ შეგნებული გადავადება ცალკე task-ად.

1. სტატიების/სიახლეების/ვიდეოების create/update/delete-ის docstring-ები
   აცხადებენ "აუდიტ-ლოგში ჩაწერას", მაგრამ კოდი არ იძახებს `log_audit`-ს
   (მხოლოდ archive/unarchive/restore/verify წერენ რეალურად). იგივე ხარვეზი
   კატეგორიების CRUD-შიც.
2. ქვიზის (`quiz`) კონტენტის რედაქტირება არ ზრდის სტატიის `version`-ს, ხოლო
   quiz-gate-ი მიბმულია სწორედ `version`-ზე — ადმინს შეუძლია ქვიზის პასუხები
   შეცვალოს იმ მომხმარებლის ქვეშ, ვინც უკვე ჩააბარა, და მას ხელახლა ჩაბარება
   არ მოეთხოვება.
3. ერთი მომხმარებლის როლის ადმინისეული ცვლილება (`PUT /api/users/{id}`) არ
   წერს აუდიტ-ლოგს და არ არისეტავს permissions-ს — შეუსაბამოა bulk
   role-reassign-თან, რომელიც ორივეს აკეთებს.
4. Permissions-ის whitelist აკლია ერთი ცნობილი ნაგულისხმევი უფლება
   (`videos.archive`) — ვერ ხერხდება მისი ხელახლა მინიჭება ამ endpoint-ის
   საშუალებით მას შემდეგ, რაც ერთხელ მოიხსნა.
5. RBAC-ს ორი პარალელური, ერთმანეთთან დაუკავშირებელი კატალოგი აქვს
   (dotted permissions `User.permissions`-ში vs colon-named კატალოგი
   DB-ში, `seed_rbac.py`-დან) — თითქმის არასდროს ემთხვევა ერთმანეთს.
   Java-ზე გადასვლისას საჭიროა ერთ კატალოგში გაერთიანება.
6. დეპარტამენტის შესატყვისობის სამი განსხვავებული წესი თანაარსებობს:
   პრეფიქს-მგრძნობიარე (compliance-ის დათვლაში, mark-read-ში,
   შეტყობინებების გავრცელებაში) vs ზუსტი-დამთხვევა (SSE stream-ის
   ფილტრში, პირდაპირი მესიჯინგის შეზღუდვაში, აუდიტ-ლოგის
   მენეჯერ-სქოუფინგში). გადაწყვიტე გაერთიანება თუ განზრახ დატოვება
   განცალკევებულად — მაგრამ არა შემთხვევით.
7. XLSX/PDF compliance ექსპორტებს არ აქვთ იგივე ვინაობის ფილტრი, რაც
   CSV ექსპორტს (რომელიც გამორიცხავს არააქტიურ/მენეჯმენტ-როლის
   მომხმარებლებს) — შეუსაბამო მონაცემები სხვადასხვა ფორმატს შორის.
8. აუდიტ-ლოგის CSV ექსპორტს არ აქვს ფორმულა-ინექციის დაცვა
   (`_sanitize_cell`-ის ეკვივალენტი), განსხვავებით ჩვეულებრივი
   ექსპორტებისგან — უსაფრთხოების ხარვეზი, რომელიც არ უნდა გადავიდეს
   ახალ სისტემაში.
9. ექსპორტის job-ებს აქვთ TTL ველი, მაგრამ არაფერი აქტიურად ასუფთავებს
   ვადაგასულ job-ებს/ფაილებს — საჭიროა რეალური reaper Java-ვერსიაში.
10. ვიდეოების დეპარტამენტის ფილტრი არ იყენებს პრეფიქს-მგრძნობიარე
    შესატყვისობას (განსხვავებით სტატიების/სიახლეებისგან) — შეუსაბამო
    ქცევა კონტენტის ტიპებს შორის.
11. Mock-SSO picker გვერდს არ აქვს production-გეიტი route-ის დონეზე
    (მხოლოდ callback-ი ჩავარდება production-ში) — გვერდი თავად მაინც
    ხელმისაწვდომია.
