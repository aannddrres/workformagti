## Active Directory (AD) ინტეგრაცია

დაკავშირებულია `java-oracle-angular-migration-initiative`-ის
მემორი-ჩანაწერთან (`auth-bypass-intentional-pending-ad.md`).
**დადასტურებულია (2026-08-11):** AD არის on-premises (არა Cloud/Entra ID);
როლებიდან მხოლოდ "ჯგუფის უფროსი" (მენეჯერი) მოდის AD-ჯგუფიდან, დანარჩენი
3 როლი (ოპერატორი/კონტენტ-ადმინი/სისტემური-ადმინი) რჩება ხელით
დანიშვნადი, დეპარტამენტი/ჯგუფი მოდის AD-ის OU-სტრუქტურიდან.

### 1. SSO პროტოკოლი — სტატუსი: 🔲 ღიაა

**კითხვა IT-სთვის:** გვაქვს თუ არა უკვე ADFS (ან სხვა SAML Identity
Provider) დაყენებული, რომელსაც სხვა შიდა აპლიკაციები იყენებენ
single sign-on-ისთვის? თუ არა — გვინდა თუ არა პირდაპირი LDAP/LDAPS
დაკავშირება domain controller-თან (Kerberos/Windows Integrated
Authentication-ის მსგავსი მექანიზმი)?

**რატომ არის საჭირო:** ეს განსაზღვრავს, Java-ბექენდში კონკრეტულად
რომელი ავთენტიფიკაციის მექანიზმი ავაშენოთ (Spring Security-ის SAML2
მოდული, თუ LDAP-ზე დაფუძნებული ავთენტიფიკაცია) — ორივეს აშენება
სხვადასხვა კოდია, ერთის ნაცვლად მეორეზე გადართვა მარტივი არ არის.

### 2. AD-ის OU-სტრუქტურა დეპარტამენტებისთვის — სტატუსი: 🔲 ღიაა

**კითხვა IT-სთვის:** როგორ არის აწყობილი Organizational Unit (OU)
სტრუქტურა AD-ში დეპარტამენტებისთვის? კონკრეტულად:

- თუ არა — რა მექანიზმით არის დღეს AD-ში წარმოდგენილი ეს დაყოფა

## Oracle-ის ვერსია

აღმოჩენილია 2026-08-15, CI-სთვის Oracle-კონტეინერის აწყობისას
(იხ. `.github/workflows/ci.yml`-ის `java-integration` job).

### 5. Oracle-ის განახლების გეგმა — სტატუსი: 🔲 ღიაა

**კითხვა IT-სთვის:** არსებობს თუ არა გეგმა Oracle 19c-დან **23ai-ზე
(ან უფრო ახალზე)** გადასვლისა? თუ დიახ — დაახლოებით როდის?

**რატომ არის საჭირო:** ეს არ არის ოპტიმიზაციის კითხვა —
**23ai-ზე აპლიკაცია საერთოდ ვერ აეშვება** მიმდინარე სახით.

მიზეზი ექსპერიმენტულად დადასტურდა: CI-ში Oracle Free 23ai-ზე გაშვებისას
221-ივე integration-ტესტი ჩავარდა ერთი და იმავე შეცდომით —

```
Schema validation: wrong column type encountered in column [is_draft]
in table [articles]; found [number (Types#NUMERIC)],
but expecting [boolean (Types#BOOLEAN)]
```

Oracle 23ai-მ დაამატა ნატიური `BOOLEAN` ტიპი. ამიტომ Hibernate ირჩევს
დიალექტს, რომელიც Java-ს `boolean`-ს `BOOLEAN`-ზე ასახავს — მაგრამ ამ
სქემის **15-ვე დროშის სვეტი `NUMBER(1)`-ია** (`V4__create_articles.sql:24`,
`V5__create_news.sql:13` და სხვ.), რადგან 19c-ს `BOOLEAN` არ გააჩნია.
`application.yml`-ის `ddl-auto: validate`-თან ერთად ეს აპლიკაციის
გაშვების მკვდარი ჩავარდნაა — და არა გაფრთხილება.

CI ამჟამად შეგნებულად **Oracle XE 21c**-ს იყენებს (19c-ის საჯარო image
არ არსებობს), რადგან 21c-საც არ აქვს ნატიური `BOOLEAN` — ანუ ეთანხმება
19c-ს ზუსტად იმ თვისებაში, რომელზეც production დგას.

**რას შევცვლით პასუხის მიხედვით:**
- თუ 19c-ზე ვრჩებით — არაფერი; ჩანაწერი რჩება როგორც ცნობილი ზღვარი.
- თუ 23ai+ იგეგმება — საჭიროა ერთ-ერთი, **განახლებამდე**:
  ა) მიგრაცია, რომელიც 15 სვეტს `BOOLEAN`-ზე გადაიყვანს, ან
  ბ) Hibernate-ის დიალექტის ცალსახა დაპინვა, რომ `boolean` კვლავ
     `NUMBER(1)`-ზე აისახოს.
  ორივე მოითხოვს დაგეგმვას და ტესტირებას — განახლების დღეს აღმოჩენა
  სისტემის გაშვების შეუძლებლობას ნიშნავს.

**პასუხი:** _(ჯერ არ არის)_

## ფაილების საცავი

დაფიქსირდა 2026-08-15, აუდიტის PR-03 / BL-09-ის გამოსწორებისას.

### 6. Oracle-ის ტაბლსფეისი ატვირთული ფაილებისთვის — სტატუსი: 🔲 ღიაა

**კითხვა IT-სთვის:**
- რამდენი ადგილი შეგვიძლია გამოვყოთ `magti_portal`-ის ტაბლსფეისში
  ატვირთული დანართებისთვის? სავარაუდო შეფასება: ~600 თანამშრომელი,
  თითო ფაილი მაქსიმუმ 10 MB, რეალურად ძირითადად სურათები და PDF —
  წელიწადში დაახლოებით **10–20 GB**-ის რიგის ზრდა.
- მოიცავს თუ არა არსებული სარეზერვო ასლის (backup) პროცედურა
  BLOB-სვეტებს? (თუ backup მხოლოდ სქემას/მცირე ცხრილებს იღებს,
  დანართები დაცული არ იქნება.)
- **ალტერნატივა:** არსებობს თუ არა კომპანიაში S3-თავსებადი ობიექტური
  საცავი (MinIO, Ceph RGW ან სხვა), ან `ReadWriteMany` StorageClass?
  თუ დიახ — ეს უკეთესი მიმართულებაა და გადავიტანთ.

**რატომ არის საჭირო:** ეს **წინაპირობაა, არა ოპტიმიზაცია.**

აქამდე ატვირთული ფაილები იწერებოდა კონტეინერის საკუთარ დისკზე
(`/app/uploads`), `VOLUME`-ის და K8s-manifest-ის გარეშე. შედეგი:
**ყოველი გადატვირთვა სამუდამოდ შლიდა ყველა დანართს** (ბაზაში ბმული
რჩებოდა და 404-ს აბრუნებდა), ხოლო ერთზე მეტი replica-ს შემთხვევაში
ფაილი ხილული იყო დაახლოებით მოთხოვნების 1/n-ზე.

რადგან ამ რეპოზიტორიაში **საერთოდ არ არის K8s-manifest-ები** და §4-ის
კითხვები კლასტერზე ჯერ ღიაა, ვერც volume-ს და ვერც S3-ს დავეყრდნობოდით —
ისეთი გამოსწორება გამოვიდოდა, რომლის მუშა ნაწილი აქედან არც ჩანს და არც
იტესტება. ამიტომ ფაილები გადავიდა **თავად Oracle-ში** (`stored_files`
ცხრილი, მიგრაცია `V31`): ბაზა ისედაც სავალდებულო დამოკიდებულებაა,
ისედაც ბექაპდება და ისედაც საერთოა ყველა replica-სთვის.

**რას შევცვლით პასუხის მიხედვით:** თუ S3 ან RWX-volume ხელმისაწვდომია,
იცვლება მხოლოდ ერთი კლასი — `storage/FileStorageService.java`; მის გარეთ
`java.nio.file.Path`-ს აღარსად ეხება კოდი.

## Reverse proxy და replica-ები

დაფიქსირდა 2026-08-15, აუდიტის SEC-04 / PR-04-ის გამოსწორებისას.

### 7. Reverse proxy-ის მისამართი — სტატუსი: 🔲 ღიაა

**კითხვა IT-სთვის:** რომელი კონკრეტული მისამართიდან (ან რომელი CIDR-იდან)
მოდის აპლიკაციამდე ტრაფიკი — ანუ რა არის nginx/ingress-ის მისამართი,
როგორც მას აპლიკაციის pod ხედავს?

**რატომ არის საჭირო:** ეს **წინაპირობაა.**

აქამდე rate limiter და აუდიტის ჟურნალი `getRemoteAddr()`-ს იყენებდნენ,
`forward-headers-strategy` კი დაყენებული არ იყო. შედეგად nginx-ის უკან
**ყველა მომხმარებელი ერთ მისამართად ჩანდა**: ერთი ადამიანი შენახული ძველი
პაროლით მთელ კომპანიას (~600 კაცი) კეტავდა, აუდიტის ყოველი ჩანაწერი კი
load balancer-ის IP-ს იწერდა.

გამოსწორებულია, მაგრამ **მუშაობს მხოლოდ მაშინ, თუ `TRUSTED_PROXIES`
დაყენებულია.** ცარიელი მნიშვნელობა (default) ნიშნავს, რომ `X-Forwarded-For`
საერთოდ იგნორირდება — ეს **შეგნებულად** არის უსაფრთხო მიმართულება, რადგან
სათაურის უპირობო ნდობა უარესი იქნებოდა: ვინც აპლიკაციას პირდაპირ მისწვდება,
ყოველ მოთხოვნაზე ახალ rate-limit ბუკეტს და ყალბ IP-ს მიიღებდა.

⚠️ მნიშვნელოვანი: მიუთითეთ **თავად proxy-ის** მისამართი, არა მთელი pod-ის
ქსელი. თუ დიაპაზონი საკმარისად ფართოა, რომ სხვა workload-ებიც მოიცვას,
მათ შეეძლებათ ორივეს გაყალბება.

### 8. რამდენი replica იგეგმება? — სტატუსი: 🔲 ღიაა

**კითხვა IT-სთვის:** Java backend გაეშვება 1 replica-ზე თუ მეტზე? თუ მეტზე —
ხელმისაწვდომია თუ არა Redis (ან სხვა საერთო cache) **Java-ს ქსელიდან**?
(`docker-compose.yml`-ის Redis ამჟამად მხოლოდ ძველ Python-აპს ემსახურება,
Java backend საერთოდ არ არის იმ ფაილში.)

**რატომ არის საჭირო:** login-ის rate limiter ინახავს მთვლელს **JVM-ის
მეხსიერებაში**. *n* replica-ზე რეალური ლიმიტი *n*-ჯერ სუსტდება, რადგან
load balancer მცდელობებს ისე ანაწილებს, რომ pod-ები ერთმანეთს ვერ ხედავენ.

ეს **შეგნებულად არ გადაწყდა** Redis-ით: Java backend-ს Redis-ის
დამოკიდებულება არ აქვს, ამ რეპოში deployment manifest არ არსებობს, სადაც
ის ჩაიწერებოდა, და ინფრასტრუქტურის დამატება, რომელსაც აქედან ვერ ვტესტავთ,
იგივე შეცდომა იქნებოდა, რაც PR-03-ში უარვყავით — კოდი გამოსწორებულად
გამოიყურება, სამუშაო ნაწილი კი უხილავია.

**რაც უნდა ითქვას გულწრფელად:** *n*×10 მცდელობა **ერთ ანგარიშზე** გაცილებით
მცირე პრობლემაა, ვიდრე ის „10 მთელი კომპანიისთვის", რომელიც შეიცვალა.
მაგრამ თუ 2+ replica იგეგმება, Redis-ზე გადატანა საჭიროა.
