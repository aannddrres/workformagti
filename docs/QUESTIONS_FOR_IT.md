### 1. კომპანიის ავტორიზაციის კონტრაქტი — სტატუსი: 🟡 ნაწილობრივ (2026-09-18)

**დადგენილი პროდუქტული პრინციპი:** პორტალი საკუთარ პაროლებს არ მართავს და
არ ინახავს. მომხმარებლის შეყვანილ მონაცემებს ან login მოთხოვნას კომპანიის
არსებული ავტორიზაციის სისტემა ამოწმებს; პორტალი მისი პასუხით უშვებს ან არ უშვებს
მომხმარებელს.

**კითხვა IT-სთვის:** ამ პროექტისთვის რომელი ტექნიკური flow არის დამტკიცებული —
backend-იდან credential verification service/LDAP/LDAPS-ის გამოძახება,
ADFS/SAML/OIDC redirect, Kerberos/Windows Integrated Authentication თუ სხვა გზა?
მოგვაწოდეთ გარემოების endpoint-ები, პროტოკოლი, request/response ან token/claim
contract, TLS/certificate მოთხოვნები და success/wrong-password/locked/disabled/
expired/MFA/timeout/unavailable პასუხების ზუსტი mapping.

თუ raw password portal-ში გაივლის, ასევე გვჭირდება კომპანიის უსაფრთხოების
სავალდებულო წესი: პაროლი არასოდეს ინახება ან ლოგირდება, request body masked-ია,
მოქმედებს TLS, timeout/retry/rate-limit კონტროლი და საჭირო security review.

**რატომ არის საჭირო:** ეს განსაზღვრავს Java backend-ში კონკრეტულად რომელი
ავთენტიფიკაციის adapter აშენდება და როგორ მოიქცევა UI თითოეულ პასუხზე. სხვადასხვა
flow სხვადასხვა კოდია და ეს არჩევანი კომპანიის ინფრასტრუქტურისგან უნდა მივიღოთ.

**პასუხი (2026-09-18, IT):** არჩეულია **OAuth2 token endpoint LDAP-grant-ით** —
ანუ backend-იდან credential verification, და არა ADFS/SAML/OIDC redirect.
პორტალი თავად იღებს ელფოსტას და პაროლს და ამოწმებს კომპანიის სერვისში:

|---|---|
| Endpoint | `https://oauth.magticom.ge/auth/oauth/token` |
| Grant type | `ldap_auth` |

როგორც დანარჩენ საიდუმლოებს (root `AGENTS.md`, „Never commit secrets").

**რაც ამ პასუხმა დაადგინა:** raw პაროლი პორტალში გაივლის. ანუ ამ კითხვის
მეორე ნახევარი — კომპანიის სავალდებულო წესი (პაროლი არ ინახება და არ

**აუცილებელი გახდა და ჯერ არ არის დადასტურებული.**

### 5. Oracle-ის განახლების გეგმა — სტატუსი: 🔲 ღიაა

**კითხვა IT-სთვის:** არსებობს თუ არა გეგმა Oracle 19c-დან **23ai-ზე
(ან უფრო ახალზე)** გადასვლისა? თუ დიახ — დაახლოებით როდის?

**რატომ არის საჭირო:** ეს არ არის ოპტიმიზაციის კითხვა —
**23ai-ზე აპლიკაცია საერთოდ ვერ აეშვება** მიმდინარე სახით.

მიზეზი ექსპერიმენტულად დადასტურდა: CI-ში Oracle Free 23ai-ზე გაშვებისას
221-ივე integration-ტესტი ჩავარდა ერთი და იმავე შეცდომით —

```
Schema validation: wrong column type encountered in column [is_draft]
in table [articles]; found [number (Types#NUMERIC)],
but expecting [boolean (Types#BOOLEAN)]
```

Oracle 23ai-მ დაამატა ნატიური `BOOLEAN` ტიპი. ამიტომ Hibernate ირჩევს
დიალექტს, რომელიც Java-ს `boolean`-ს `BOOLEAN`-ზე ასახავს — მაგრამ ამ
სქემის **15-ვე დროშის სვეტი `NUMBER(1)`-ია** (`V4__create_articles.sql:24`,
`V5__create_news.sql:13` და სხვ.), რადგან 19c-ს `BOOLEAN` არ გააჩნია.
`application.yml`-ის `ddl-auto: validate`-თან ერთად ეს აპლიკაციის
გაშვების მკვდარი ჩავარდნაა — და არა გაფრთხილება.

CI ამჟამად შეგნებულად **Oracle XE 21c**-ს იყენებს (19c-ის საჯარო image
არ არსებობს), რადგან 21c-საც არ აქვს ნატიური `BOOLEAN` — ანუ ეთანხმება
19c-ს ზუსტად იმ თვისებაში, რომელზეც production დგას.

**რას შევცვლით პასუხის მიხედვით:**
- თუ 19c-ზე ვრჩებით — არაფერი; ჩანაწერი რჩება როგორც ცნობილი ზღვარი.
- თუ 23ai+ იგეგმება — საჭიროა ერთ-ერთი, **განახლებამდე**:
  ა) მიგრაცია, რომელიც 15 სვეტს `BOOLEAN`-ზე გადაიყვანს, ან
  ბ) Hibernate-ის დიალექტის ცალსახა დაპინვა, რომ `boolean` კვლავ
     `NUMBER(1)`-ზე აისახოს.

## Reverse proxy და replica-ები

დაფიქსირდა 2026-08-15, აუდიტის SEC-04 / PR-04-ის გამოსწორებისას.

### 7. Reverse proxy-ის მისამართი — სტატუსი: 🔲 ღიაა

**კითხვა IT-სთვის:** რომელი კონკრეტული მისამართიდან (ან რომელი CIDR-იდან)
მოდის აპლიკაციამდე ტრაფიკი — ანუ რა არის nginx/ingress-ის მისამართი,
როგორც მას აპლიკაციის pod ხედავს?

**რატომ არის საჭირო:** ეს **წინაპირობაა.**

აქამდე rate limiter და აუდიტის ჟურნალი `getRemoteAddr()`-ს იყენებდნენ,
`forward-headers-strategy` კი დაყენებული არ იყო. შედეგად nginx-ის უკან
**ყველა მომხმარებელი ერთ მისამართად ჩანდა**: ერთი ადამიანი შენახული ძველი
პაროლით მთელ კომპანიას (~600 კაცი) კეტავდა, აუდიტის ყოველი ჩანაწერი კი
load balancer-ის IP-ს იწერდა.

გამოსწორებულია, მაგრამ **მუშაობს მხოლოდ მაშინ, თუ `TRUSTED_PROXIES`
დაყენებულია.** ცარიელი მნიშვნელობა (default) ნიშნავს, რომ `X-Forwarded-For`
საერთოდ იგნორირდება — ეს **შეგნებულად** არის უსაფრთხო მიმართულება, რადგან
სათაურის უპირობო ნდობა უარესი იქნებოდა: ვინც აპლიკაციას პირდაპირ მისწვდება,
ყოველ მოთხოვნაზე ახალ rate-limit ბუკეტს და ყალბ IP-ს მიიღებდა.

⚠️ მნიშვნელოვანი: მიუთითეთ **თავად proxy-ის** მისამართი, არა მთელი pod-ის
ქსელი. თუ დიაპაზონი საკმარისად ფართოა, რომ სხვა workload-ებიც მოიცვას,
მათ შეეძლებათ ორივეს გაყალბება.

**2026-09-23 — დაზუსტება (P04):** გზა არის თანამშრომელი → ingress →
`portal-frontend` nginx → backend. გვჭირდება backend-ის მიერ დანახული
**frontend peer-ის** ზუსტი მისამართი/CIDR და `X-Forwarded-For`-ის ყველა
სანდო შუალედური proxy hop. გთხოვთ მიუთითოთ SNAT, ingress-ის header policy
და backend-მდე სხვა workload-ების წვდომის ქსელური შეზღუდვა. მხოლოდ
ingress-ის ნდობა frontend peer-ს არ მოიცავს და მომხმარებლის IP დაიკარგება.
მთელი pod CIDR-ის ან `0.0.0.0/0`-ის ბრმად ნდობა გამოსავალი არ არის.

დასრულებულად ჩაითვლება ორი კლიენტის განსხვავებული IP აუდიტში და მათი
შესვლის ლიმიტების გამიჯვნის ცდა, აგრეთვე ყალბი მარცხენა header-ისა და
არასანდო პირდაპირი peer-ის უარყოფის მტკიცებულება. თუ კლიენტები ერთ NAT
მისამართს იზიარებენ, მიუთითეთ ეს შეზღუდვაც. რეალური ქსელის პასუხი კვლავ ღიაა.

### 11. Stable ID-ები, ცვლილებების feed და deactivation — სტატუსი: 🔲 ღიაა

კითხვა №2 ეხება იმას, **სად** ცხოვრობს ორგანიზაციული სტრუქტურა AD-ში. ეს
კითხვა ეხება იმას, **როგორ წავიკითხოთ ის საიმედოდ** — ორივე პასუხი გვჭირდება,
სანამ sync adapter დაიწერება.

**კითხვა IT-სთვის:**

1. რა არის დეპარტამენტის, ჯგუფისა და მომხმარებლის **უცვლელი (stable)
   იდენტიფიკატორი** AD-ში — `objectGUID`, `distinguishedName`, თუ სხვა?
   კონკრეტულად: რომელი მათგანი **არ იცვლება** ჯგუფის გადარქმევისას ან
   მომხმარებლის სხვა OU-ში გადატანისას?
2. როგორ მივიღოთ **ცვლილებების feed** — სრული სკანირება ყოველ ჯერზე, თუ
   ინკრემენტული მექანიზმი (`uSNChanged`, DirSync, Change Notifications)?
   რა სიხშირით არის დასაშვები მოთხოვნა? პროდუქტის სამიზნეა deactivation-ის,
   ჯგუფისა და დეპარტამენტის ცვლილების მაქსიმუმ 5–15 წუთში ასახვა. რომელი
   event/delta გზა ასრულებს ამას დაახლოებით 600 მომხმარებელზე და რა იქნება მისი
   გაზომილი დატვირთვა?
3. რა ნიშნავს **deactivation**-ს AD-ში: `userAccountControl`-ის disabled ბიტი,
   ობიექტის წაშლა, თუ სპეციალურ OU-ში გადატანა? წაშლილი ობიექტი რამდენ ხანს
   რჩება ხელმისაწვდომი (tombstone lifetime) და როგორ გაუქმდება უკვე გაცემული
   portal session/token? თუ 5–15 წუთიანი სამიზნე შეუძლებელია, მოგვაწოდეთ მიზეზი,
   დატვირთვის შეფასება და ყველაზე სწრაფი უსაფრთხო ინტერვალი.
4. თანამშრომელი შეიძლება ერთდროულად რამდენიმე ჯგუფის წევრი იყოს AD-ში? თუ კი,
   რომელი ჩაითვლება მის **ძირითად** ჯგუფად?

**რატომ არის საჭირო:**

- პორტალის მოდელი ითხოვს, რომ ჯგუფის იდენტობა **უფროსისგან და სახელისგან
  დამოუკიდებელი** იყოს — გადარქმევამ არ უნდა გატეხოს არც ერთი ისტორიული

### 12. SMS-გეითი და მობილურის ნომერი AD-იდან — სტატუსი: 🔲 ღიაა

**პროდუქტის იდეა (მფლობელი, 2026-08-31):** როცა ოპერატორი სავალდებულო
მასალას გაეცნობა და დაადასტურებს, მის მობილურზე მივიდეს SMS — რომ თვითონაც
ჰქონდეს დადასტურება, რომ გაცნობა დაფიქსირდა. ნომერი AD-იდან მოდის.

**რატომ ეკითხება ეს IT-ს და არა კოდს:** დღეს backend **არცერთ გარე სისტემას
არ მიმართავს** — არავითარი გამავალი კავშირი. SMS პირველი იქნება. ე.ი. ეს
არა მხოლოდ ინტეგრაციაა, არამედ **ქსელის და უსაფრთხოების გადაწყვეტილებაც**.

---

#### ა. გეითი და ინტეგრაციის წესი

1. რომელი SMS-გეითი გამოიყენება და **რა პროტოკოლით** — HTTP/REST, SMPP, თუ
   შიდა სერვისი? მოგვაწოდეთ მისამართი და, თუ არსებობს, API-ს აღწერა.
2. **ავთენტიფიკაცია:** API-გასაღები, mTLS, IP-ის allowlist, თუ სხვა? სად
   ინახება საიდუმლო — იმავე Kubernetes Secret-ში, თუ ცალკე?
3. **გამგზავნის სახელი (sender ID):** რა დაწერია SMS-ის გამგზავნად? საჭიროა
   თუ არა ცალკე რეგისტრაცია?
4. **ქსელი:** დაშვებულია თუ არა გამავალი კავშირი პორტალის namespace-იდან ამ
   მისამართზე? საჭიროა თუ არა NetworkPolicy-ის ან firewall-ის ცვლილება?
   *(დღემდე ამ აპლიკაციას გამავალი კავშირი საერთოდ არ სჭირდებოდა.)*

6. **მიწოდების დადასტურება:** გვიბრუნებს თუ არა გეითი delivery report-ს?

**⚠️ უსაფრთხოება — IT-მ აუცილებლად უნდა იცოდეს.** წერილში გამოგზავნილი client
credential `InfoPortal`-ის კი არა, **`WebAdmin`-ისაა**, მისი საიდუმლო ტრივიალურად
გამოსაცნობი ნაგულისხმევი მნიშვნელობაა, და ის **მოქმედია**. (მნიშვნელობა აქ
განზრახ არ წერია — root `AGENTS.md`, „Never commit secrets“.) წერილის ნიმუში
ორივეს ერთად აგზავნის — ამ გასაღებს სათაურში და `client_id: InfoPortal`-ს სხეულში.
**ზუსტად ასე გაგზავნილ მოთხოვნაზე სერვერი პასუხობს `401 invalid_client` —
„Given client ID does not match authenticated client“** (დომენით და უდომენოდ,
ორივე შემთხვევაში; პაროლი ამ დროს არ მოწმდება — კლიენტის შემოწმება წინ უსწრებს).
ანუ ნიმუში, როგორც დაწერილია, ვერ იმუშავებს: გასაღები `WebAdmin`-ად შემოდის, და
`InfoPortal`-ად შესასვლელად `InfoPortal`-ის საკუთარი გასაღებია საჭირო. `client_id`-ის
გარეშე სერვერი `WebAdmin`-ის სახელით უშვებს — ზემოთ აღწერილი გაზომვა სწორედ ასეთია,
ამიტომ ველების სია და სახელის ფორმატი `InfoPortal`-ისთვის შეიძლება განსხვავდებოდეს. ის
ნებისმიერი თანამშრომლის პაროლით გასცემს 12-საათიან ტოკენს `read write trust`
scope-ით და იმ თანამშრომლის CCare-ის უფლებებით (გადახდები, აბონენტის მონაცემები).
ანუ პორტალი, რომელიც ამ კლიენტით შევა, სხვა სისტემისთვის ვარგის ტოკენებს
მიიღებს. საჭიროა: **პორტალისთვის ცალკე კლიენტი** (`InfoPortal`), მინიმალური
scope-ით (`user_info`/`read`), `WebAdmin`-ის საიდუმლოს შეცვლა.

**რას ნიშნავს ადაპტერისთვის:** შესვლა მხოლოდ ვინაობის დასადასტურებლად — პასუხიდან
ვიღებთ login-ს, ელფოსტას და `userId`-ს (მდგრადი იდენტიფიკატორი JIT-ისთვის), ტოკენებს
**არ ვინახავთ, არ ვლოგავთ და არსად ვაგზავნით**; პორტალს თავისი სესია აქვს
(PO-27). `503` HTML „სერვისი მიუწვდომელია“-ა და არასწორ პაროლად არ ითვლება.
