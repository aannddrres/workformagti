გვატყობინებს, თუ რომელიმე მოთხოვნას რეგულაცია ან არსებული გარემო ზღუდავს.

## 2. კოდში ოფიციალურად დარჩენილი გადაწყვეტილებები

### PO-01 / D-2 — ✅ გადაწყვეტილია: სახელობითი სია leadership scope-ით

**მფლობელის გადაწყვეტილება (2026-08-22):** ჯგუფის უფროსი ხედავს, მის ჯგუფში
ვინ წაიკითხა; დეპარტამენტის ხელმძღვანელი ხედავს თავისი დეპარტამენტის ყველა
ჯგუფს; SYSTEM_ADMIN ხედავს ყველას. ეს არის მარტივი scope-პირამიდა. მხოლოდ
`content.manage` სახელობით წვდომას არ იძლევა. კონტენტის მმართველს, რომელსაც
შესაბამისი leadership scope არ აქვს, რჩება მხოლოდ საერთო რაოდენობები.

სახელობით სიაში თანამშრომლის სახელი საკმარისია; email არ გამოჩნდება.

#### განხილული ვარიანტები

დღეს კონტენტის ადმინისტრატორს შეუძლია კომპანიის მასშტაბით ნახოს თანამშრომლის
სახელი, email, დეპარტამენტი, წაკითხვის დრო და დაგვიანება.

**A — სრული სახელობითი სია კონტენტის მმართველს.**

- კონტენტის მმართველი ხედავს ყველა თანამშრომლის დეტალს.
- ავტორს ადვილად შეუძლია კონკრეტულ ადამიანს შეახსენოს.
- სანაცვლოდ `content.manage` უკვე თანამშრომლების ქცევის მონიტორინგსაც ნიშნავს.

**B — კონტენტის მმართველს მხოლოდ საერთო რიცხვები; სახელები მხოლოდ ლიდერს თავის scope-ში.**

- ავტორი ხედავს, მაგალითად, „600-დან 480-მა წაიკითხა“.
- ჯგუფის/დეპარტამენტის უფროსი ხედავს, კონკრეტულად ვინ არ წაიკითხა მხოლოდ თავის ხალხში.
- კონტენტის უფლება თანამშრომლების პერსონალურ მონაცემს აღარ ხსნის.

**C — სახელები მხოლოდ SYSTEM_ADMIN-ს.**

- ყველაზე მკაცრი privacy მოდელია.
- ლიდერი ვეღარ მიიღებს თავისი გუნდის ჩამორჩენილთა ავტომატურ სიას.

**რეკომენდაცია:** B — კონტენტის გუნდს რჩება შედეგის საზომი, ხოლო სახელობითი
კონტროლი ხელმძღვანელობის პასუხისმგებლობას მიჰყვება.

**საბოლოო პასუხი:** არჩეულია B, დეპარტამენტის ხელმძღვანელის ზედა scope-ით და
email-ის გარეშე.

### PO-02 / D-4 — ✅ გადაწყვეტილია: დანართი მხოლოდ შესულ თანამშრომელს

**მფლობელის გადაწყვეტილება (2026-08-22):** არჩეულია B. სტატიაზე ატვირთული
სურათი, PDF ან სხვა დანართი მხოლოდ პორტალში ავტორიზებულ თანამშრომელს გაეხსნება.
დაკოპირებული `/uploads/<uuid>` მისამართი login-ის გარეშე არ იმუშავებს. საჯარო/
დაცული ტიპების არჩევანი არ ემატება.

#### განხილული ვარიანტები

დღეს ვინც `/uploads/<uuid>` ბმულს გაიგებს, ფაილს login-ის გარეშე გახსნის. UUID
ძნელი გამოსაცნობია, მაგრამ გაჟონილი ბმული მომავალშიც მუშაობს.

**A — დავტოვოთ როგორც არის.**

- სტატიაში სურათი და ფაილი ყველაზე მარტივად იტვირთება.
- ბმულის გადაგზავნით ფაილს სისტემის გარეთაც გახსნიან.
- გათიშული თანამშრომლის ხელში დარჩენილი ბმულიც მუშაობს.

**B — ყველა დანართი მხოლოდ ავტორიზებული თანამშრომლისთვის.**

- გაჟონილი URL თავისით საკმარისი აღარ არის.
- logout/deactivation-ის შემდეგ ფაილიც აღარ იხსნება.
- frontend/download/image-loading ქცევა უნდა შეიცვალოს და დაიტესტოს.

**C — ორი ტიპი: საჯარო და დაცული დანართი.**

- ავტორი ატვირთვისას ირჩევს ტიპს.
- მოქნილია, მაგრამ UI, წესები და შეცდომის რისკი მნიშვნელოვნად იზრდება.

**რეკომენდაცია:** B, რადგან ეს შიდა კორპორაციული პორტალია.

**საბოლოო პასუხი:** B.

### PO-03 / D-5 — ✅ გადაწყვეტილია: ერთი საერთო `content.manage`

**მფლობელის გადაწყვეტილება (2026-08-22):** არჩეულია A. `content.manage` ერთი
საერთო უფლებაა და ერთად რთავს კონტენტის შექმნას, გამოქვეყნებას, სხვისი მასალის
რედაქტირებასა და კატეგორიების მართვას. ცალკე permission-ები/ჩამრთველები არ
ემატება.

#### განხილული ვარიანტები

დღეს `content.manage` ერთად ნიშნავს: კონტენტის შექმნას, გამოქვეყნებას, სხვისი
მასალის რედაქტირებას და კატეგორიების მართვას.

**A — ერთი საერთო უფლება დავტოვოთ.**

- ადმინის ეკრანი მარტივი რჩება: ადამიანს ან შეუძლია კონტენტის სრულად მართვა, ან არა.
- ვერ გვეყოლება ადამიანი, რომელიც მხოლოდ წერს, მაგრამ ვერ აქვეყნებს.
- ნაკლები კოდი, ნაკლები კონფიგურაციის შეცდომა.

**B — დავყოთ უფლებებად.** მაგალითად:

- `content.create` — შექმნა/საკუთარის რედაქტირება;
- `content.publish` — გამოქვეყნება;
- `content.edit_any` — სხვისი მასალის შეცვლა;
- `categories.manage` — კატეგორიების მართვა.

შედეგად კონტროლი ზუსტია, მაგრამ ადმინის UI და permission audit უფრო რთულდება.

**რეკომენდაცია:** A, თუ რეალურად არ გყავს განსხვავებული „ავტორი“, „რედაქტორი“ და
„გამომქვეყნებელი“ პერსონები. B მხოლოდ მაშინ, თუ ეს როლები ბიზნესში არსებობს.

**საბოლოო პასუხი:** A.

### PO-04 / D-6 — ✅ გადაწყვეტილია: მომხმარებლისთვის ყველაფერი ქართულად

**მფლობელის გადაწყვეტილება (2026-08-22):** პროექტი მხოლოდ ქართულ
ენაზეა; CSV/Excel export-ის ყველა მომხმარებლისთვის ხილული სვეტის სათაური
ქართულად იქნება. ენის არჩევანი არ ემატება. ტექნიკური API field-ები და კოდის
შიდა identifier-ები შეიძლება ინგლისურად დარჩეს, რადგან მომხმარებელს არ უჩანს.

#### განხილული ვარიანტები

**A — ინგლისურად.** ტექნიკური დამუშავება და სხვა სისტემაში import უფრო მარტივია,
მაგრამ რიგითი ქართველი მომხმარებლისთვის ნაკლებად მოსახერხებელი.

**B — ქართულად.** Excel-ში გახსნისას ადამიანისთვის გასაგებია, მაგრამ automation/
import-ს სტაბილური ინგლისური სახელები აღარ აქვს.

**C — არჩევადი ენა ან ორივე ენა.** საუკეთესო UX, მაგრამ ემატება UI პარამეტრი,
თარგმანი და მეტი ტესტი.

**რეკომენდაცია:** B, თუ export ძირითადად ადამიანისთვისაა; A, თუ სხვა პროგრამა
კითხულობს; C მხოლოდ ორივე რეალური საჭიროებისას.

**საბოლოო პასუხი:** პროექტი მხოლოდ ქართულ ენაზეა; მომხმარებლისთვის ხილული
export-ის სათაურებიც ქართულად იქნება.

### PO-05 / D-7 — ✅ გადაწყვეტილია: პირადი messaging წაიშლება, broadcast დარჩება განცხადებად

**მფლობელის გადაწყვეტილება (2026-08-22):** თანამშრომლებს შორის პირადი
შეტყობინებები პორტალში არ გვჭირდება და შესაბამისი endpoint-ები/მოდელი უნდა
წაიშალოს. Broadcast სხვა ფუნქციაა: ის არის პორტალის საერთო ინფორმაცია,
რომელიც ყველა ავტორიზებულ თანამშრომელს მთავარ გვერდსა და პროფილში უჩანს.
მაგალითად: ოფისი დაიკეტა ან რომელიმე მიმართულებაზე ტექნიკური პრობლემაა.
„საერთო“ არ ნიშნავს, რომ განცხადება ინტერნეტში ან ავტორიზაციის გარეშე გამოჩნდება.

Broadcast ყოველთვის პასიურია და მომხმარებელი მას ვერ ხურავს, თუმცა პორტალის
გამოყენებას არ უნდა უშლიდეს ხელს: აკრძალულია modal/overlay და ეკრანის
დამბლოკავი ფორმა. ის გამოქვეყნებისთანავე ჩნდება, დასრულების დრო სავალდებულოა და
გამომქვეყნებელს მისი დროზე ადრე მოხსნაც შეუძლია. Broadcast აუდიტორიებად არ
იყოფა — ის ყოველთვის ყველა ავტორიზებულ თანამშრომელს ეხება.

გამოქვეყნება შეუძლიათ `content.manage`-ის მქონე კონტენტის მმართველებს, მოქმედ
ძირითად ან დროებით ჯგუფის უფროსებს და `SYSTEM_ADMIN`-ს. ლიდერის Broadcast-იც
კომპანიის საერთო განცხადებაა და მხოლოდ საკუთარ ჯგუფზე არ იზღუდება.

განხორციელებისას broadcast პირადი `messaging` domain-ისგან უნდა განცალკევდეს და
ქართულ UI-ში „განცხადებად“/„საერთო ინფორმაციად“ გამოჩნდეს, არა პირად შეტყობინებად.

რომ შესაძლო ხარვეზი ჟურნალში გამოჩენილიყო და არა მომხმარებელთან.
პროდუქტის მფლობელმა უარყო: ფაილი, რომელიც სხვისია, არ უნდა იხსნებოდეს
პირველივე დღიდან, და ორკვირიანი დაყოვნება დაკვირვების სანაცვლოდ
ქოლ-ცენტრისთვის არასწორი გაცვლაა.

**რაც ამას ენაცვლება:** პირველი კვირის ხელით დაკვირვება ორ სიგნალზე —
აუდიტში `FILE_ACCESS_DENIED` ისეთ ფაილზე, რომელიც ხილულ სტატიაშია, და
აპლიკაციის log-ში `WARN ... healing from scan`. ორივე აღწერილია
`docs/ROLLOUT_ROLLBACK_KA.md`-ში, „DEC-P01".

**უკან დაბრუნება:** `ROLLOUT_FILE_ENTITLEMENT: "false"` და restart.
