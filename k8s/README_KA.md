## სამი ველი, რომელსაც განსაკუთრებული ყურადღება სჭირდება

### IT-06 — `TRUSTED_PROXIES`

ცარიელი დატოვება **უსაფრთხოა, მაგრამ ორ რამეს აფუჭებს:**

1. აუდიტის ჟურნალში ყველა მოქმედება ingress-ის IP-დან ჩანს, არა თანამშრომლის.
2. შესვლის ლიმიტი მთელ კომპანიას ერთ კალათაში აგდებს — ათი არასწორი პაროლი
   ერთი ადამიანისგან ყველას ბლოკავს.

ბრმად ნდობა უარესი იქნებოდა (ნებისმიერს შეეძლებოდა IP-ის გაყალბება), ამიტომ
ნაგულისხმევი მნიშვნელობა არ არსებობს. **შეავსეთ.**

### IT-07 — `SECRET_KEY`

ეს ხელს აწერს ყველა სესიას. აპლიკაცია **უარს ამბობს ჩართვაზე**, თუ მნიშვნელობა
სუსტია — 48 სიმბოლოზე მოკლე, შაბლონური სიტყვის შემცველი, ან ერთფეროვანი.

გენერაცია:

```bash
python -c "import secrets; print(secrets.token_urlsafe(64))"
```

**git-ში არ ჩაწეროთ.** შექმენით ცალკე:

```bash
kubectl -n <namespace> create secret generic portal-backend-secrets \
  --from-literal=SECRET_KEY='...' \
  --from-literal=ORACLE_DB_PASSWORD='...'
```

თუ კლასტერს sealed-secrets ან external-secrets აქვს — ის ჯობია და არაფერი
გიშლით ხელს.

### IT-12 / IT-14 — TLS

**TLS აუცილებელია.** სესიის cookie `Secure`-ია, ე.ი. ბრაუზერი მას მხოლოდ
HTTPS-ზე გააგზავნის, ხოლო backend უარს ამბობს გაშვებაზე `COOKIE_SECURE=false`-ით.

თუ ingress მხოლოდ HTTP-ზე გაიხსნება, პორტალი შესვლისას „გაფუჭებული" გამოჩნდება.
ეს განზრახაა: სესია ღია ტექსტში არ უნდა მოგზაურობდეს.

## გაშვება

```bash
# 1. Secret — ცალკე, git-ის გარეშე
kubectl -n <namespace> create secret generic portal-backend-secrets \
  --from-literal=SECRET_KEY='...' \
  --from-literal=ORACLE_DB_PASSWORD='...'

# 2. დანარჩენი
kubectl apply -k k8s/

# 3. დაკვირვება
kubectl -n <namespace> rollout status deploy/portal-backend
kubectl -n <namespace> rollout status deploy/portal-frontend
```

**პირველი გაშვება ნელია და ეს ნორმალურია.** backend-ის pod-ი Flyway-ს უშვებს,
რომელიც ბაზის სქემას აწყობს (V1-დან V46-მდე). Flyway ექსკლუზიურ ბლოკს იღებს,
ამიტომ რამდენიმე pod ერთმანეთს არ უშლის — ერთი აკეთებს, დანარჩენები ხედავენ და
გამოტოვებენ. `startupProbe`-ს ამისთვის 5 წუთი აქვს გამოყოფილი.

## შემოწმება, რომ მართლა მუშაობს

```bash
# ორივე ცოცხალია და მზადაა
kubectl -n <namespace> get pods -l app.kubernetes.io/part-of=magti-portal

# backend ბაზას წვდება (ok = კავშირი აქვს)
kubectl -n <namespace> exec deploy/portal-backend -- \
  wget -qO- http://localhost:8080/api/health

# უსაფრთხოების პარამეტრები ჩაირთო
kubectl -n <namespace> logs deploy/portal-backend | grep "Startup security config"
```

ბოლო ბრძანება ყველაზე მნიშვნელოვანია: აპლიკაცია გაშვებისას თვითონ ბეჭდავს,
რა რეჟიმშია. თუ იქ `dev-login=enabled` ან `env=development` წერია — **გაშვება
შეაჩერეთ**, კონფიგურაცია არასწორია.

## რაც ჯერ კიდევ ღიაა

ეს ფაილები აპლიკაციას უშვებს. სამი რამ მათ გარეთაა და კომპანიის გადაწყვეტილებას
საჭიროებს:

1. **Oracle-ის backup და აღდგენა.** ბაზა თქვენია; საკითხავია, ეს სქემა backup-ის
   გრაფიკში შედის თუ არა და აღდგენა ოდესმე შემოწმებულა თუ არა. აპლიკაციის მხრიდან
   არაფერია გასაკეთებელი.
2. **CI/CD.** GitHub-ის მხარე დაწერილია (ტესტები, ბილდი, E2E). აკლია ბოლო ნაბიჯი —
   image-ის ატვირთვა თქვენს registry-ში და `kubectl apply`. ეს ერთი job-ია, ოღონდ
   თქვენი მისამართებით.
3. **AD/SSO.** დღეს `/api/auth/sso/start` პასუხობს 503-ს: *„კომპანიის ავტორიზაციის
   სერვისი ჯერ არ არის დაკავშირებული"*. განზრახ — სანამ არ ვიცით, რომელი
   პროტოკოლით უკავშირდება (SAML, OIDC თუ LDAP). იხ. `docs/QUESTIONS_FOR_IT.md` §1.

**მესამის გარეშე პორტალში შესვლა შეუძლებელია.** პირველი ორის გარეშე გაშვება
შესაძლებელია, მაგრამ არ არის რეკომენდებული.

## NetworkPolicy

განზრახ არ დამატებულა. სწორი წესები დამოკიდებულია იმაზე, როგორ არის თქვენი
namespace-ები დაყოფილი და სად დგას Oracle. საჭირო კავშირები ესაა:

- ingress → `portal-frontend:8080`
- `portal-frontend` → `portal-backend:8080`
- `portal-backend` → Oracle (1521 ან რაც IT-04-შია)
- DNS ორივესთვის

სხვა კავშირი არცერთს არ სჭირდება.
