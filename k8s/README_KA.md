## სამი ველი, რომელსაც განსაკუთრებული ყურადღება სჭირდება

### IT-06 — `TRUSTED_PROXIES`

ცარიელი დატოვება **უსაფრთხოა, მაგრამ ორ რამეს აფუჭებს:**

1. აუდიტის ჟურნალში ყველა მოქმედება frontend nginx-ის IP-დან ჩანს, არა თანამშრომლის.
2. შესვლის ლიმიტი მთელ კომპანიას ერთ კალათაში აგდებს — ათი არასწორი პაროლი
   ერთი ადამიანისგან ყველას ბლოკავს.

გზაა **თანამშრომელი → ingress → portal-frontend nginx → backend**.
backend-ის უშუალო peer არის frontend-ის pod-ის რეალურად დანახული მისამართი
(SNAT-ის შემთხვევაში — გადათარგმნილი მისამართი). მხოლოდ ingress-ის ნდობა
არ კმარა: ასეთ დროს `X-Forwarded-For` მთლიანად იგნორირდება. ჩამონათვალში
შეიტანეთ frontend peer-იც და ჯაჭვის ყველა სანდო proxy hop, რომელიც
თანამშრომლის IP-მდე უნდა გამოიტოვოს `ClientIpResolver`-მა.

მხოლოდ სინთეზური მაგალითი, **კლასტერში პირდაპირ არ გადაიტანოთ**:

```bash
# frontend peer: 10.42.0.7; ingress hop: 10.43.0.4
TRUSTED_PROXIES=10.42.0.7,10.43.0.4
```

DevOps-მა უნდა მოგვცეს რეალური IP/CIDR-ები, SNAT-ის აღწერა და ingress-ის
header-ის დამუშავების წესი. backend-მდე ქსელური წვდომა მხოლოდ უფლებამოსილ
proxy-ებს ჰქონდეთ. მთელი pod ქსელი ან `0.0.0.0/0` ბრმად არ ჩაწეროთ:
იმავე დიაპაზონის სხვა workload-ს IP-ის გაყალბება შეეძლება.

მიღების ცდა: ორი განსხვავებული კლიენტის IP აუდიტშიც განსხვავდება; ერთის
შესვლის ლიმიტი მეორეს არ ეხება; გაყალბებული მარცხენა header და არასანდო
პირდაპირი peer შედეგს ვერ ცვლის. ერთ NAT IP-ს მიღმა ორი თანამშრომელი
ამ მექანიზმით ვერ გაირჩევა — ეს ცალკე ქსელური შეზღუდვაა.

### IT-07 — `SECRET_KEY`

ეს ხელს აწერს ყველა სესიას. აპლიკაცია **უარს ამბობს ჩართვაზე**, თუ მნიშვნელობა
სუსტია — 48 სიმბოლოზე მოკლე, შაბლონური სიტყვის შემცველი, ან ერთფეროვანი.

სამივე მნიშვნელობა შეინახეთ კომპანიის secret manager-ში; `SECRET_KEY` შექმენით
კრიპტოგრაფიული შემთხვევითი გენერატორით (მინიმუმ 48 სიმბოლო). თუ კლასტერში
external-secrets ან sealed-secrets გამოიყენება, Secret მისი საშუალებით მიაწოდეთ.

**git-ში არ ჩაწეროთ.** ხელით შექმნისთვის სამივე მნიშვნელობა წინასწარ მოათავსეთ
მხოლოდ შემსრულებლისთვის წაკითხვად დროებით ფაილებში, კომპანიის დამტკიცებული გზით.
ქვემოთ შეცვალეთ მხოლოდ ფაილების გზები; მნიშვნელობები არ ჩასვათ ბრძანების
არგუმენტებში, shell history-ში ან ტერმინალის გამოტანაში. ფაილს არ დაუმატოთ
ბოლო newline — ისიც Secret-ის მნიშვნელობის ნაწილი გახდება.

```bash
kubectl -n <namespace> create secret generic portal-backend-secrets \
  --from-file=SECRET_KEY=/secure/temporary/session-key \
  --from-file=ORACLE_DB_PASSWORD=/secure/temporary/database-password \
  --from-file=OAUTH_SECRET=/secure/temporary/infoportal-credential
```

`OAUTH_SECRET` არის IT-ის მიერ მოწოდებული InfoPortal-ის Basic credential:
`client:secret`-ის base64, `Basic ` პრეფიქსის გარეშე. `--from-file`-ს გადაეცემა
ზუსტად ეს ტექსტი; Kubernetes-ისთვის დამატებით base64-ად არ გადააქციოთ.
დროებითი ფაილები მოაშორეთ კომპანიის წესით. უკვე არსებული Secret არ წაშალოთ:
მნიშვნელობების შეცვლა ცალკე, შეთანხმებული როტაციაა; `SECRET_KEY`-ის შეცვლა
არსებულ სესიებს აუქმებს.

### IT-12 / IT-14 — TLS

**TLS აუცილებელია.** სესიის cookie `Secure`-ია, ე.ი. ბრაუზერი მას მხოლოდ
HTTPS-ზე გააგზავნის, ხოლო backend უარს ამბობს გაშვებაზე `COOKIE_SECURE=false`-ით.

თუ ingress მხოლოდ HTTP-ზე გაიხსნება, პორტალი შესვლისას „გაფუჭებული" გამოჩნდება.
ეს განზრახაა: სესია ღია ტექსტში არ უნდა მოგზაურობდეს.

## გაშვება

```bash
# 1. Secret — შექმენით ზემოთ, IT-07-ში აღწერილი სამი-key რეცეპტით

# 2. დანარჩენი
kubectl apply -k k8s/

# 3. დაკვირვება
kubectl -n <namespace> rollout status deploy/portal-backend
kubectl -n <namespace> rollout status deploy/portal-frontend
```

**პირველი გაშვება შეიძლება ნელი იყოს.** backend-ის pod-ი Flyway-ს უშვებს,
რომელიც ბაზის სქემას აწყობს (ყველა მიგრაცია, V1-დან). Flyway ექსკლუზიურ ბლოკს იღებს,
ამიტომ რამდენიმე pod ერთმანეთს არ უშლის — ერთი აკეთებს, დანარჩენები ხედავენ და
გამოტოვებენ. `startupProbe`-ს ამისთვის 5 წუთი აქვს გამოყოფილი.

**V49-ის წინ არსებული ბაზის წაკითხვითი შემოწმება:** აუდიტის `row_hash` ახალი
უნიკალური ინდექსით იძებნება. DBA-მ განახლებამდე შეამოწმოს დუბლიკატების რაოდენობა:

```sql
SELECT COUNT(*) AS duplicate_hash_groups FROM (
  SELECT row_hash FROM audit_logs WHERE row_hash IS NOT NULL
  GROUP BY row_hash HAVING COUNT(*) > 1
);
```

პასუხი **0** უნდა იყოს. სხვა პასუხზე მიგრაცია შეჩერდება; ძველი ჩანაწერები
არ წაიშალოს და hash-ები არ გადაითვალოს. DBA/უსაფრთხოების გუნდმა მიზეზი
მტკიცებულებასთან ერთად უნდა გამოიკვლიოს. ახალ ცარიელ სქემაზე ეს ნაბიჯი
არ არის საჭირო. გარედან დასაცავი აუდიტის საკონტროლო ასლის საკითხი
`docs/QUESTIONS_FOR_IT.md` №14-შია.

**V50-ის ექსპორტის rollout:** V50 ამატებს worker-ის მფლობელსა და 90-წამიან
lease-ს. ახალი და ძველი backend worker-ები ერთდროულად არ უნდა ამუშავებდნენ
ექსპორტს: ძველი კოდი lease-ს არ ამოწმებს და დაგვიანებულ ფაილს მაინც
გამოაქვეყნებს. განახლებამდე მიმდინარე ექსპორტები დაასრულეთ/გააჩერეთ, შემდეგ
გადართეთ backend-ები. დაკარგული ახალი worker-ის სამუშაო მაქსიმუმ დაახლოებით
120 წამში `failed` ხდება (15-წამიანი heartbeat, 30-წამიანი შემოწმება),
ერთი საათი ჩანს და მომხმარებელი ახალ ექსპორტს იწყებს. Staging-ზე შეამოწმეთ
pod-ის შეწყვეტა და მეორე replica-ის ცოცხალი ექსპორტი; timeout-ები იქ გაზომეთ.

## შემოწმება, რომ მართლა მუშაობს

```bash
# ორივე ცოცხალია და მზადაა
kubectl -n <namespace> get pods -l app.kubernetes.io/part-of=magti-portal

kubectl -n <namespace> logs deploy/portal-backend | grep "Startup security config"
```

რა რეჟიმშია. თუ იქ `dev-login=enabled` ან `env=development` წერია — **გაშვება
შეაჩერეთ**, კონფიგურაცია არასწორია.

## მონიტორინგი

backend აქვეყნებს Prometheus-ის მეტრიკებს:

```
port 8080, path /actuator/prometheus
```

pod-ს უკვე აქვს `prometheus.io/scrape` annotation-ები — ე.ი. pod-discovery-ზე
აწყობილი Prometheus თვითონ იპოვის. თუ `ServiceMonitor`/`PodMonitor` გიყენიათ
(kube-prometheus-stack), annotation-ები იგნორირდება — მიუთითეთ იმავე პორტსა
და გზაზე.

**რას აჩვენებს:** მოთხოვნების სიხშირე და ხანგრძლივობა (route-ების მიხედვით),
შეცდომების რაოდენობა სტატუსების მიხედვით, JVM-ის მეხსიერება, და **კავშირების
პულის მდგომარეობა** — ბოლო ყველაზე მნიშვნელოვანია, რადგან პულის ამოწურვა
ზუსტად ისე გამოიყურება, როგორც „ბაზა ნელია".

> ### ⚠ `/actuator` გარეთ არ უნდა გავიდეს
>
> ეს გზა **ტოკენის გარეშე პასუხობს**. ეს უსაფრთხოა მხოლოდ იმიტომ, რომ:
>
> - Ingress frontend-ის Service-ს აქვეყნებს, backend-ისას — არა;
> - frontend-ის nginx მხოლოდ `/api/`-სა და `/uploads/`-ს გადასცემს.
>
> ე.ი. `/actuator` მხოლოდ კლასტერის შიგნიდან მიიწვდომება. **თუ Ingress-ს
> `/actuator` დაუმატებთ, ეს დაცვა იშლება.**
>
> მეტრიკებში პერსონალური მონაცემები არ ხვდება: მისამართები შაბლონად
> იწერება (`/api/articles/{id}`), და არა კონკრეტული ID-ით. ამას
> `MetricsEndpointIntegrationTest` ამოწმებს.
>
> დანარჩენი Actuator-ის გზები (`/env`, `/heapdump`, `/beans`) **დახურულია** —
> იმავე ტესტით დადასტურებული.

### alert: ნელი ჩაწერა

ერთ E2E გაშვებაში ★-ის `POST /api/favorites` 5 წამს გაგრძელდა და კლიენტმა
მიატოვა (nginx 499, A06). 500 კონტროლირებად ცდაში აღარ განმეორებულა
(უმაღლესი 81 ms), ამიტომ მიზეზი უცნობია. მფლობელის გადაწყვეტილებით
(2026-09-25) production-ში იგივე ნიშანი alert-ით უნდა დავიჭიროთ:

```promql
max by (instance, method, uri) (
  http_server_requests_seconds_max{application="magti-portal",
    method=~"POST|PUT|PATCH|DELETE", uri=~"/api/.*",
    uri!~"/api/upload|/api/auth/login"}
) > 5
```

Micrometer-ის `_max` ბოლო ~2 წუთის მაქსიმუმია, ამიტომ ერთი ნელი მოთხოვნაც
ჩანს. ორი გზა განზრახ გამორიცხულია: ატვირთვის დროში ფაილის გადაცემაც შედის,
შესვლის დროში კი კომპანიის სერვერის პასუხიც.

nginx-ის მხრიდან იგივე ნიშანი ლოგის პლატფორმაში უნდა დაიჭიროს (რომელ
პლატფორმაში — [IT №10](../docs/QUESTIONS_FOR_IT.md)). ეს არის frontend-ის
`audit_timing` სტრიქონი, რომელშიც `path` `/api/`-ით იწყება, `method`
ჩაწერისაა და `request_time` ≥ 5. **499 თავისთავად ნიშანი არ არის.**
გვერდის დატოვება მიმდინარე მოთხოვნას 499-ით წყვეტს, heartbeat-ის `POST`-საც.
ასეთი მოთხოვნის `request_time` 0–16 ms-ია (გაზომილია 2026-09-26). alert-ზე
რეაგირება: [საოპერაციო სახელმძღვანელო](../docs/IT_OPERATIONS_RUNBOOK_KA.md#პრობლემების-მოძიება).

## რაც ჯერ კიდევ ღიაა

შესავსები ველების შევსების შემდეგ ეს მანიფესტები აპლიკაციას ტექნიკურად გაუშვებს. ქვემოთ ჩამოთვლილი საკითხები მაინც კომპანიის მიღებას მოითხოვს; ლოკალური გაშვება მათ ვერ ხურავს:

1. **Oracle-ის backup და აღდგენა.** ბაზა თქვენია; საკითხავია, ეს სქემა და BLOB-ები backup-ის
   გრაფიკში შედის თუ არა და აღდგენა ოდესმე შემოწმებულა თუ არა. DBA-ს staging-ზე
   restore rehearsal და პორტალის health/კონტენტის/ფაილის smoke check სჭირდება;
   [IT-ის საოპერაციო სახელმძღვანელო](../docs/IT_OPERATIONS_RUNBOOK_KA.md#backup-restore-და-rollback-ის-საზღვრები).
2. **CI/CD.** GitHub-ის მხარე დაწერილია (ტესტები, ბილდი, E2E). აკლია ბოლო ნაბიჯი —
   image-ის ატვირთვა თქვენს registry-ში და `kubectl apply`. ეს ერთი job-ია, ოღონდ
   თქვენი მისამართებით.
3. **კომპანიის ავტორიზაცია.** ადაპტერი დაწერილია (2026-09-21): შესვლის ფორმა
   პაროლს კომპანიის OAuth2 სერვისით (`ldap_auth`) ამოწმებს, როლს ყოველ შესვლაზე
   იქიდან იღებს, ტოკენებს კი არ ინახავს. გასაშვებად აკლია IT-ის ორი რამ:
   **InfoPortal-ის კლიენტის გასაღები** (IT-15) და **როლების შექმნა** მათ სისტემაში
   (IT-16). ტესტისას სერვისი მხოლოდ Magti-ს ქსელიდან პასუხობდა — backend-ს
   გამავალი 443 სჭირდება (იხ. NetworkPolicy).

**მესამის გარეშე პორტალში შესვლა შეუძლებელია.** პირველი ორის გარეშე გაშვება
შესაძლებელია, მაგრამ არ არის რეკომენდებული.

## NetworkPolicy

განზრახ არ დამატებულა. სწორი წესები დამოკიდებულია იმაზე, როგორ არის თქვენი
namespace-ები დაყოფილი და სად დგას Oracle. საჭირო კავშირები ესაა:

- ingress → `portal-frontend:8080`
- `portal-frontend` → `portal-backend:8080`
- `portal-backend` → Oracle (1521 ან რაც IT-04-შია)
- `portal-backend` → `oauth.magticom.ge:443` — კომპანიის ავტორიზაცია. მის
  გარეშე შესვლის ყოველი ცდა 503-ით მთავრდება („სერვისი დროებით მიუწვდომელია“),
  და არა „არასწორი პაროლით“
- DNS ორივესთვის

სხვა კავშირი არცერთს არ სჭირდება.
